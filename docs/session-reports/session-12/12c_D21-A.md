## Q4. Where the vocabulary is enforced

**The live schema** (`sqlite_master`, `mode=ro`) of `paper_events`:

```sql
        to_state    TEXT    NOT NULL CHECK (to_state IN ('eligible', 'abstract_out', 'full_text_out', 'parsed', 'extracted', 'extraction_failed', 'full_text_not_obtainable', 'parse_failed', 'input_exceeds_context', 'audited_ai')),
        ...
        reason_code TEXT,
        ...
        -- R39 / S3h: a reason for exactly the failure tokens, and for no other.
        CHECK (
            (to_state IN ('extraction_failed', 'full_text_not_obtainable', 'parse_failed', 'input_exceeds_context') AND reason_code IS NOT NULL)
         OR (to_state NOT IN ('extraction_failed', 'full_text_not_obtainable', 'parse_failed', 'input_exceeds_context') AND reason_code IS NULL)
        ),
```

Its triggers are `paper_events_no_update` and `paper_events_no_delete`, both append-only. The CHECK
is defined in `engine/migrations/019_paper_state_axes.py` and carried forward by `020` and `022`
(`grep -l "reason_code IS NOT NULL" engine/migrations/*.py`).

**The schema requires `reason_code` to be non-null for a failure token, but does not close its
values.** The closed set is enforced only in Python:
- `plan_extraction_events` raises `ValueError(… "is not in the closed set (F9)")`.
- `write_paper_event` (`engine/core/events.py`) inserts `reason_code` unvalidated.

**A new reason code would need no migration.** D21 needs none anyway (Q3).

`eligible_paper_ids` (`engine/core/effective.py:520`):

> "The corpus: every paper whose ELIGIBILITY axis reads `eligible` (S3h/A9). … Processing outcome is
> deliberately not consulted: a paper whose extraction failed is in the corpus and is reported by its
> reason."

**A paper with a prior failed processing event is re-selected.** That event is on the processing axis
(eligibility is unchanged) and carries no claim, so the reuse key cannot match. The paper is refused
again, or extracted once its text is restored.

Consequence: under any write-at-selection fix, a paper whose text stays refused gets a new
`extraction_failed` event **on every run**. `paper_events` is append-only, so the log grows by one
row per run per refused paper. This is the same as today's in-loop path.

## Q8. Classification — INFERRED

**(i) Fixable within R122.**
- The writer exists: `outcome_for_exception` maps every `ParsedTextError` to
  `PaperFailure(… exc.reason_code …)`, and `write_extraction_events` writes it as a processing-axis
  `extraction_failed` event (Q2).
- All three errors already carry codes in the closed set, `EXTRACTION_REASONS` (Q3).
- The schema requires only a non-null `reason_code` for `extraction_failed`, so no migration is needed
  (Q4).

What the fix must decide, recorded here and not proposed:
1. **Where the write goes.** The point after selection in `_stage_extract` covers the empty-selection
   early return. The in-loop path alone does not (Q5). The selection-less path in
   `_run_extraction_unlocked` is a second site.
2. **Double-writing.** A paper refused at selection is not in `to_extract`, so the in-loop writer
   never sees it. A write at selection therefore does not duplicate the in-loop write within one run.
3. **One event per run per still-refused paper** (Q6), which is the existing in-loop behaviour.
