### W1-F5-C1 — The truncation ceiling ignores a Modelfile `PARAMETER num_ctx`; the post-call check is then blind
- **File / function:** `engine/utils/ollama_client.py` — `effective_ceiling`, `n_ctx_train`, `_check_input_was_read`
- **Pattern:** i (and iv: the term is never read)
- **Evidence level:** conditional (condition: a model the run uses carries `PARAMETER num_ctx` in its Modelfile, lower than its trained context, and the request sends no `options.num_ctx`. Not established for any installed model — no `show` call permitted. That Ollama applies a Modelfile `num_ctx` when the request sets none is my knowledge of the runtime, not measured here.)
- **Evidence:** `effective_ceiling`:
  ```python
  trained = n_ctx_train(model)
  num_ctx = _option(options, "num_ctx")
  if num_ctx is not None:
      return min(trained, num_ctx)
  terms = [trained, SERVER_DEFAULT_CTX]
  env = server_context_length()
  ```
  Three terms: trained context, the request option, the service environment. `n_ctx_train` reads only `modelinfo` keys ending `.context_length` from `_client.show(model)`; the same response's Modelfile parameters are never looked at. Docstring: "The token count at which the runtime starts cutting this call's input." Module docstring: "an input the runtime truncated or silently dropped part of fails loudly after the call". `_check_input_was_read` raises only on `if count >= ceiling:` or `if count < floor:` (`floor = chars * RATIO_DROP`, 0.10).
  The premise is a dated measurement, not a check: `docs/session-reports/INPUT-FIT-01_phase-1_readout.md`, "Effective ceilings": "no Modelfile sets `num_ctx`". CLAUDE.md (R66) itself names the source the guard omits: `num_ctx` is recorded as `"unset"` / `modelfile_or_server`.
- **What goes wrong:** with a Modelfile `num_ctx` of N below the trained context, the runtime cuts at N while the guard's ceiling stays at the trained value. A truncated call returns `prompt_eval_count` = N < ceiling, and passes unless N is also under 10% of the character count (observed ratios are ~0.19–0.26, so anything short of losing roughly half the text passes). The call is recorded `completed` and its output is stored as an extraction or screening decision made on the whole text.
- **Refutation tried:** searched `effective_config.py` and `ollama_preflight.py` for any Modelfile/parameters read — none. The live service drop-in sets no `OLLAMA_CONTEXT_LENGTH` (read as a file), so on live the ceiling is the trained context alone. The readout's "no Modelfile sets `num_ctx`" makes this not live on the measured day; nothing re-asserts it at run open, for a re-pulled model, a custom model, or another review's models. No ruling found accepting the omission (plan grep for Modelfile + num_ctx: no hit).
- **Tests:** `tests/test_ollama_input_fit.py` — `StubClient.show` returns only `modelinfo={"arch.context_length": …, "arch.embedding_length": 4096}`, so no test can present a Modelfile parameter; `test_the_ceiling_is_the_trained_context_when_nothing_else_is_set` pins the three-term rule. Unpopulated-world fixture.
- **Existing row:** new
- **Proposed class / package:** 1 / P1 — a silently truncated model input stored as a normal result, on any review whose model declares its own context; conditional, so priority follows the condition.

### W1-F5-C2 — The restart gate is a probe that is released before the restart, not a hold across it
- **File / function:** `engine/utils/ollama_lock.py` — `check_experiment_lock`, `foreign_lock_held`; `engine/utils/ollama_client.py` — `_restart_ollama_and_retry`
- **Pattern:** i
- **Evidence level:** code order
- **Evidence:** `check_experiment_lock`:
  ```python
  fcntl.flock(fd, fcntl.LOCK_EX | fcntl.LOCK_NB)
  fcntl.flock(fd, fcntl.LOCK_UN)
  return False
  ```
  ("on success the probe lock is released immediately"). `_restart_ollama_and_retry`: `if foreign_lock_held(): raise RuntimeError(…)`, then a log line, then `subprocess.run(["sudo", "systemctl", "restart", "ollama"], timeout=30, …)`, then `time.sleep(10)`. Nothing holds the lock between the probe and the end of the restart. Stated guarantees: `foreign_lock_held` docstring, "restarting under someone else's experiment is the bug this module prevents"; `_restart_ollama_and_retry` docstring, "restarting the service out from under *someone else's* multi-hour experiment destroys it".
- **What goes wrong:** a non-holder's watchdog exhausts with the lock free; it probes (free) and restarts. A second process that takes `hold_experiment_lock()` any time after the probe and before the service is back (up to ~40 s) is a lock holder restarted beneath, and neither side sees a refusal. The holder's first calls fail as connection errors and are retried, so the outcome is loud or absorbed, not a wrong result.
- **Refutation tried:** looked for a hold on the restarter's side (taking the lock non-blocking and keeping it across the restart would close the window) — there is none; `hold_experiment_lock` is never called from `ollama_client.py`. When the restarter itself holds the lock the window does not exist (exclusive lock). `extractor.restart_ollama` uses the same probe (outside this lot, not chased).
- **Tests:** `tests/test_restart_recovery_guard.py::test_restart_proceeds_when_lock_is_free` and `::test_restart_refused_under_foreign_lock` test the two static states; no test acquires the lock between the gate and `subprocess.run`.
- **Existing row:** extends A1 (A1 is the never-holding workload; this is a holder that acquires after the probe — a different mechanism, same gate)
- **Proposed class / package:** 2 / P2 — a narrow race ending in loud connection failures for the late holder; no stored result is made wrong.

### W1-F5-C4 — Every restart-path ending is reported as "timed out after N attempts + restart", and a restart that happened is recorded nowhere in the manifest
- **File / function:** `engine/utils/ollama_client.py` — `ollama_chat` (`except FuturesTimeoutError` branch), `_restart_ollama_and_retry`
- **Pattern:** ii, iv
- **Evidence level:** code order
- **Evidence:** `ollama_chat`:
  ```python
  except RuntimeError:
      raise TimeoutError(
          f"Ollama call timed out after {1 + max_retries} attempts + restart "
          f"(model={model}, {paper_label}, limit={effective_timeout}s)"
      )
  ```
  `_restart_ollama_and_retry` raises `RuntimeError` for four different endings: opt-out ("restart refused: … is set"), foreign lock ("restart refused: another process holds the experiment lock"), `subprocess.run` failing ("Ollama restart failed"), and `except Exception as post_exc:` around the final call ("Post-restart Ollama call failed"), which wraps any exception — a refused connection because 10 s was not enough, an `ollama.ResponseError`, a second watchdog timeout alike. The recorder writes `detail = f"{type(exc).__name__}: {exc}"` from the outer `TimeoutError`, whose text is the same in all four cases; the `RuntimeError` survives only as `__context__` and a log line. On the successful ending, `return _finish(response)` records `completed` with nothing saying the service was restarted under the run.
- **What goes wrong:** the `run_calls` row for a call whose restart was refused says "+ restart" although no restart ran; a call that failed after the restart for a non-timeout reason is recorded as a timeout; and a run's manifest cannot show that the server (and so the loaded model) was restarted mid-run. The callers map `TimeoutError` to the paper outcome `model_call_failed`, so the four causes also collapse there.
- **Refutation tried:** `tests/test_restart_recovery_guard.py::test_refusal_surfaces_as_timeout_from_ollama_chat` pins the type (`TimeoutError`), which CLAUDE.md states; nothing pins or checks the message or the recorded detail. F14's accounting note ("one `run_calls` row stands for up to four requests") is the neighbouring fact; it does not cover the cause being lost or the restart being unrecorded.
- **Tests:** the test above (type only); `tests/test_ollama_client.py::test_watchdog_retries_then_raises` (`match="timed out"`).
- **Existing row:** extends F14 (its accounting edge: the recorded detail misstates the cause, and a successful restart leaves no manifest trace)
- **Proposed class / package:** 3 / P7 — recorded telemetry and wording; no stored value changes.

- **File / function:** `engine/utils/ollama_client.py` — `ollama_chat`, `except (httpx.TimeoutException, httpx.ConnectError) as exc:`

- **Evidence level:** code order
- **Evidence:** the pinned client (`ollama` 0.6.1, `ollama/_client.py`, `Client._request_raw`): `except httpx.ConnectError: raise ConnectionError(CONNECTION_ERROR_MESSAGE) from None`. A refused connection therefore reaches `ollama_chat` as the builtin `ConnectionError` and lands in the generic `except Exception` arm ("Ollama call failed"), not the arm that names `httpx.ConnectError` ("Ollama HTTP timeout"). - **Refutation tried:** `httpx.TimeoutException` (read timeout) is not wrapped by the library, so that half of the arm is live. `tests/test_ollama_client.py::test_transient_failure_then_success` already uses builtin `ConnectionError`, the real vocabulary.
- **Tests:** none asserts which arm a connection failure takes.
- **Existing row:** new
- **Proposed class / package:** 3 / P7 — dead exception arm and log label.
