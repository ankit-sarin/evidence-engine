## Q2 — FT screening, and where a search start ends

`run_pipeline` does **not** run FT screening, and does not run acquisition (read: the stage sequence above;
`_stage_parse`'s own message says "PDF acquisition is manual for v1"). FT screening is the separate CLI
`python -m engine.agents.ft_screener`, which opens its own `screening` manifest.

The gate after SCREEN:

```python
        target_stage = STAGES[start_idx] if skip_to else "parse"
        if target_stage in _POST_SCREENING_STAGES:
            if not is_adjudication_complete(db._conn):
                blocker = get_current_blocker(db._conn)
                if blocker:
                    ...
                    _finish_review_run(db, run_id, "interrupted",
                                       reason=rm.REASON_BLOCKED_ADJUDICATION)
                    return
```

Where a search start ends (probe, check off, **real gates**):

| start | end | what ran |
|---|---|---|
| none | `interrupted`, `blocked:adjudication` | SEARCH, SCREEN (4 screening calls, 2 papers → `ABSTRACT_SCREENED_IN`), then the gate |
| `--skip-to search` | **`completed`** | SEARCH, SCREEN, PARSE, EXTRACT (2 papers, 80 field events), AUDIT, EXPORT |
| `--skip-to screen` | **`completed`** | the same |

In both `completed` runs all twelve workflow stages were still `pending`.

**Where it should end:** at the adjudication gate, as the default start does. After it the review needs
human adjudication, acquisition, PARSE, then the FT CLI before anything is eligible to extract.

Why the two `--skip-to` starts pass (read): `target_stage` is `"search"` or `"screen"`, which is not in
`_POST_SCREENING_STAGES`, so the adjudication check is skipped. The second gate then asks
`get_current_blocker`, which returns the **first** pending stage (`ABSTRACT_SCREENING_COMPLETE`), and the
gate only stops on `AUDIT_QUEUE_EXPORTED` or `AUDIT_REVIEW_COMPLETE`:

```python

                if blocker and blocker["stage_name"] in (
                    "AUDIT_QUEUE_EXPORTED", "AUDIT_REVIEW_COMPLETE",
                ):
```

so it does not stop either. (The probe's reviews were seeded with eligible papers so that extraction had
work; on a genuinely fresh review EXTRACT would select nothing, but the gates are skipped just the same.)

## Q3 — the abstract-screening write path

`engine/agents/screener.py::run_screening(db, spec)` takes **no `run_id`**. It writes (read; counts from the
probe):

- `db.add_screening_decision(pid, 1, d1.decision, d1.rationale, primary_model)` — one
  `abstract_screening_decisions` row per pass. Columns (probe): `id, paper_id, pass_number, decision,
  rationale, model, decided_at`. **No `run_id`.**
- `db.update_status(pid, "ABSTRACT_SCREENED_IN" | "ABSTRACT_SCREENED_OUT" | "ABSTRACT_SCREEN_FLAGGED")`.
- a checkpoint file beside the database, deleted on completion.

It writes **no paper event** (probe: zero `paper_events` for the two screened papers). Under the pipeline's
active run its calls are recorded in `run_calls` under `abstract_screen_primary`, but with **`paper_id`
NULL** (probe: four rows, all NULL) — `screen_paper` does not pass `paper_id` to `ollama_chat`. So a
decision row can be tied to its run only by timestamp.

It does not complete `ABSTRACT_SCREENING_COMPLETE`: only `run_verification` does, and nothing calls that
(E9).

**Would declaring the stages alone make the run complete correctly?** The stages are already declared;
what is missing is the preflight row. Declaring it makes the **default** start run SCREEN and stop at the
adjudication gate, which is the designed end. It does not make the run *correct* in the engine's own
terms: the decisions carry no run provenance, no eligibility event is written, the calls are not
attributable per paper, verification never runs, and the run is labelled `extraction`. Those are S4's.
And it opens the gate bypass in Q2 for the two `--skip-to` starts.

## Q4 — F2, the spec-less preflight calls

`engine/utils/ollama_preflight.py`:

```python
def require_preflight(models: list[str], runner_name: str, timeout: int = 30,
                      *, spec=None) -> None:
    ...
    check_ollama_env()
    result = preflight_check(models, timeout=timeout, spec=spec)
    if not result.success:
        msg = (
            f"{runner_name} pre-flight check failed: {result.error_summary}. "
            f"Aborting — fix model availability before retrying."
        )
        logger.error(msg)
        raise RuntimeError(msg)
```

The two calls, `engine/agents/screener.py`:

```python
    primary_model = spec.screening_models.primary
    ...
    require_preflight([primary_model], runner_name="Abstract screening")
```

```python
    verification_model = spec.screening_models.verification
    ...
    require_preflight([verification_model], runner_name="Abstract verification")
```

**What falls back.** Not the model set: each list is read from the spec and passed explicitly. With no
`spec=`, `check_model` resolves `stage_config("preflight", None, model=model_name)`, so the probe's
**options** (`temperature`, `num_predict`) and **`keep_alive`** come from the spec model's declared
defaults, while the run's `preflight:<model>` row is resolved **with** the spec (`resolve_run`:
`stage_config("preflight", spec, model=m)`).

**On the live spec there is no difference** (probe): for both abstract models the spec and spec-less
resolutions give equal kwargs and equal `options_hash` —
`{'model': …, 'options': {'temperature': 0, 'num_predict': 4}, 'keep_alive': -1}` — because the spec sets
neither a `preflight` nor an `ollama` block. A spec that set either would send a probe whose options its
own stage row does not record, with nothing to refuse it (the send check compares the model only).

**Does it contradict "no entry point falls back to spec-less defaults"?** In the letter, yes: these are
entry-point paths that resolve a stage without the spec. C41, C52 and C53's rows are each scoped to named
sites and none names preflight; C49 records the same thing for the FT site only. So it is a gap in the
claim's coverage, not a reopened row. **I3 is false** on "model set"; true on options and `keep_alive`.
Three sites in all: `run_screening`, `run_verification`, `run_ft_screening`.

## Q7 — remedy options (nothing acted on)

**(a) Declare the screening preflight when the start is at or before SCREEN.** In `_open_run_manifest`,
add the abstract primary's model to `preflight` when `abstract_screen_primary` is among the stages.
*Files:* `scripts/run_pipeline.py`; tests. *Tests:* new — the manifest from `search` / `screen` carries
`preflight:<screening primary>`; a default-start run on a scratch review screens and closes
`interrupted`, `blocked:adjudication`. *Size:* about three lines of code. *What it leaves:* everything in
Q3; and it **opens the Q2 gate bypass** for `--skip-to search|screen`, which today's defect is masking.
It should not land without F1 ruled.

**(b) SCREEN opens its own `screening` manifest.** *May one invocation hold two sequential manifests?*
Mechanically yes: `open_run` and `activate` / `deactivate` carry no single-run assumption, and tests open
two manifests on one connection in sequence. But `run_pipeline` is built around one `run_id`: opened once
before the first stage, threaded to every stage, closed once, with one interrupt path. Two manifests means
restructuring that open / close / interrupt logic, and deciding what the second manifest of an invocation
records if the first ends at a gate. R258's wording is also "one screening manifest per CLI invocation".
*Files:* `scripts/run_pipeline.py`, probably `engine/agents/screener.py` (to take a `run_id`); tests in
`test_run_pipeline_closes.py`, `test_run_interrupts.py` and new ones. *Size:* moderate to large, and it
overlaps S4 and S6.

**(c) `run_pipeline` refuses a start at or before SCREEN, at open, with a clear message.** *Files:*
`scripts/run_pipeline.py`; tests. *Tests:* new — default, `search` and `screen` starts refuse before a
manifest is written, naming the reason. *Size:* small. *What it does:* replaces an accidental refusal with
a deliberate one and closes the gate bypass by construction; a narrowing, and the PI's call under X3.

**What I would take: (a), together with a fix for F1**, as one row or two adjacent commits. (a) is the
smallest change that makes the default start do what it was designed to do — screen, then stop at the
human gate — and it is the option consistent with X3 (R342 stands: the engine, not Run 7, is the product).
It must not land alone: on its own it turns two CLI starts from "refused by accident" into "runs
extraction past both human gates". If F1 is not wanted before the tag, (c) is the safe alternative,
because it leaves no start that reaches the bypass.

Q5's re-raise is independent of the choice and small; with (a) the screening preflight is declared, so
the wrapped message stops appearing on this path, but any other undeclared preflight would still read as
"fix model availability".

## Findings

**F1 — candidate row (defect candidate, outside C55's text; not acted on).** *`run_pipeline --skip-to
search` and `--skip-to screen` skip both human gates: the adjudication check keys on the start stage

pending.* Established by probe with the preflight check neutralised: both starts closed `completed`,
having extracted two papers, with twelve workflow stages `pending`. Today C55's failure stops both starts

the FT site C49 already names. No wire difference on the live spec.

**F3 — abstract-screen `run_calls` rows carry no `paper_id`** (Q3). With S4.

**F4 — the audit-review gate's blocker test reads the first pending stage, not the audit stages' own
state** (Q2). Part of F1's cause; it also means a review whose earlier workflow stage is pending is never
stopped by this gate.
