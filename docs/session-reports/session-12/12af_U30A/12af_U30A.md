## The blocking answer

An interrupt during a cloud run is not rolled back anywhere. `run_arm`'s `finally: rm.close_run(...)` then commits whatever the interrupt
left open on the connection, because `close_run` ends with `conn.commit()` (`run_manifest.py:924`).

The worst case is (A), the entry's test (FAKE §5). An interrupt between `store_result`'s extraction INSERT and its span INSERTs commits an
extraction row with no spans. `get_pending_papers` then treats the paper as done, so it is never re-extracted.

A second state is also committed, which the row does not name (C). If the interrupt lands inside the event writer's savepoint, the
writer rolls back to its savepoint but leaves the legacy INSERTs open, and `close_run` commits them. The paper then has its legacy rows,
no claims, and is done.

The run closes `failed`, with reason `KeyboardInterrupt`.

SIGTERM and SIGHUP are a separate case: the cloud entry point installs no handler (`scripts/run_cloud_extraction.py`, census (d)). So a
tmux kill or a closed terminal ends the process with no `finally` run at all. Nothing uncommitted survives, but the manifest is left open
with no end.

## §2 Q1 — The status

**The tokens.** `END_STATUSES = ("completed", "failed", "interrupted", "aborted")` (`engine/migrations/022_run_kinds_and_audit_tables.py:137`,
mirrored at `run_manifest.py:75`). 022's CHECK requires a reason for `aborted`, refuses one for `completed`, and permits either for
`failed` and `interrupted` (`close_run`'s docstring, `run_manifest.py:906–908`).

**`close_run`, whole** (`run_manifest.py:904–924`, CODE ORDER): it validates the status, runs `UPDATE run_manifests SET ended_at = ?,
end_status = ?, end_reason = ? WHERE run_id = ?`, then `conn.commit()`. It does nothing about a transaction already open on the connection.
That transaction is committed with the close.

**The local pipeline on an interrupt** (`scripts/run_pipeline.py:217–229`, CODE ORDER):
```python
    except (KeyboardInterrupt, rm.RunInterrupted) as exc:
        # C47: an interrupt closes the run 'interrupted' with its signal's
        # reason. Roll back first, then check: an uncommitted write is never
        # committed by the close, and a close the interrupt caught before its
        # commit is rolled back with it — a rolled-back close is not a close
        # (12a-C47-R2). A committed close (a gate stop) stands. Then the
        # interrupt propagates to main().
        if db._conn.in_transaction:
            db._conn.rollback()
        if not rm.is_closed(db._conn, run_id):
            _finish_review_run(db, run_id, "interrupted",
                               reason=rm.interrupt_reason(exc))
```
- **The reason** comes from `interrupt_reason`: "interrupt:SIGINT", "interrupt:SIGTERM" or "interrupt:SIGHUP" (`run_manifest.py:946–948`).
- **SIGTERM and SIGHUP** arrive as `RunInterrupted`, a `BaseException` raised by `interrupt_signals`' handler (`:131–140`, `:997–1015`),
  installed only by command-line mains (`run_pipeline.py:639`, `ft_screener.py:681`).
- **`main` returns `128 + signum`, and `exit_process` ends the process** (`run_pipeline.py:645–657`; `run_manifest.py:967–995`). The FT
  CLI does the same (`ft_screener.py:623–630`, `:684`, `:700`).
- **What "interrupted" means there:** an operator stop (a signal), rolled back first, its signal named in the reason. It is distinct from
  `failed`, an exception from the run itself.

**The entry's "closes `interrupted`" against R625(a)(8).** No contradiction. R625(a)(8) rules the reason form for failed closes. The entry
asks the cloud runner to do what C47 made the other two runners do.
- Today a cloud interrupt records `end_status 'failed'`, `end_reason 'KeyboardInterrupt'` (FAKE §5, all three cases).
- Under the entry it would record `'interrupted'`, `'interrupt:SIGINT'`.
- Either changes `tests/test_failed_close_reason.py::test_a_cloud_arm_interrupted_closes_failed_naming_the_interrupt`, which pins the
  former.

## §3 Q2–Q6

### Q2 — Where an interrupt can land

The handlers it meets, all CODE ORDER:
- `send`'s two `except Exception` (`base.py:194`, `:202`) and `store_result`'s `except Exception:` / `self._conn.rollback()` (`:507–508`):
  a KeyboardInterrupt or RunInterrupted passes them.
- The transports' `except Exception` in the retry loop and around the store (`openai_extractor.py:211`, `:243`;
  `anthropic_extractor.py:232`, `:266`): it passes them.
- The event writer's `except BaseException:` (`extraction_events.py:720–724`): it catches the interrupt, does `ROLLBACK TO
  extraction_events` and `RELEASE`, then re-raises.
- `run_arm`'s `except BaseException as exc:` (`scripts/run_cloud_extraction.py:121–125`): it sets `failed` and the reason, then re-raises.
- `run_arm`'s `finally: rm.close_run(...)` (`:126–127`), then `extractor.close()` (`:128–129`).

Python's sqlite3 opens a transaction at the first INSERT, so an INSERT not yet committed is open on `extractor._conn` until a commit or
rollback. `rm.record_call` commits at the end of every row (`run_manifest.py:1058`), and `close_run` commits (`:924`).

| Legacy rows and spans, no claims | **yes** | row 9; FAKE (C) |

### Q4 — Which interrupts

- **SIGINT (Ctrl-C).** Python's default handler raises `KeyboardInterrupt` in the main thread. It passes every `except Exception` and
  reaches `run_arm`'s `except BaseException` and `finally` (FAKE §5).
- **SystemExit.** A `BaseException`, so it would be handled as an interrupt is. Nothing on the cloud run path raises it.
- **SIGTERM and SIGHUP.** The cloud entry point installs no handler: `main()` runs `run_arm` directly (`scripts/run_cloud_extraction.py:211`),
  with no `rm.interrupt_signals()`, and `if __name__ == "__main__": main()` (`:214–215`) does not use `exit_process`. Census (d): the only
  `interrupt_signals` users are `run_pipeline.py:639` and `ft_screener.py:681`. Under the default action the process ends at once and no
  `finally` runs.
  - A `tmux kill-session` sends SIGHUP to the pane's processes, and so does a closed terminal. The entry point runs under
    `maybe_background` (`:189–190`).
  - What survives is everything already committed; whatever was open is discarded when the file is next opened. The manifest has no end
    (Q2 row 13).
- **The experiment lock.** The cloud entry point does not take it: R625(a)(3), "cloud-only entry points do not hold the lock". Nothing to
  release.
- **The connection.** On a raised interrupt, `extractor.close()` runs (`:128–129`) after `close_run`. On a signal death the operating
  system closes it.

### Q5 — The row's first half

`rm.activate` does `_ACTIVE.set((conn, run_id))` (`run_manifest.py:1077–1080`). It gives two things, CODE ORDER:
- **`ollama_chat`'s recording and per-call checks.** `record_active_ollama_call` and `check_declared_call` read `_ACTIVE`. The cloud path
  makes no Ollama call, so this adds nothing there.
- **`write_field_event`'s field-name check** (`events.py:340–344`): with a run active and registered, a claim on a field outside the run's
  codebook is refused with `UnknownFieldName`. Since U40 the cloud store writes claims through `legacy_record`, which iterates `expected`
  only (`extraction_events.py:304` `for name in expected:`), so a cloud claim never carries a name outside the codebook's expected set. The
  check would never fire on the cloud path.

**R798(e)'s premise is half right.** `enforce_completeness` refuses MISSING names (it raises `IncompleteExtractionError`) and duplicates
(`DuplicateFieldError`). An UNEXPECTED name is only logged, "unexpected field(s) %s dropped (R118)" (`completeness.py:212–215`), and
`store_result` still inserts every span it was given (`for span in spans:`, `base.py:461`). That is N46, carried with U28 and not fixed in
the code. An unexpected field therefore reaches `cloud_evidence_spans` and never reaches the claims.

So nothing is owed to the first half by activation. It could be noted as answered: claims are filtered by `legacy_record`. The
legacy-table half of N46 is a separate, existing item.

### Q6 — What a rollback must cover

- **A rollback in `store_result` on any exit** (`except BaseException`, or a `finally` that rolls back when the store did not commit):
  - It would undo rows 7–9: the extraction and any spans, with the events already rolled back by the writer.
  - It would not undo the paper's `run_calls` rows, each committed by `record_call` at its send. They record calls that were made, which
    is correct.
  - It would not undo the instance's kept reference and chain, which are memory only and end with the process.
- **A rollback in `run_arm` before its close** (C47's form: `if conn.in_transaction: conn.rollback()`, then `is_closed`, then close):
  - It would cover every point at once, store or not, including row 12, a close caught before its commit.
  - It would also roll back row 4's pending `run_calls` INSERT, so a call that was made would lose its row.
- **The transports' handlers** need nothing: they already let a `BaseException` through.
- **U29's send and an interrupted call.** `send` records only on `Exception` (R800(b)). A KeyboardInterrupt inside `_create` (row 2) leaves
  a call that may have been transmitted with no row. Recording it would mean catching `BaseException` in `send`, writing `error` with
  detail `KeyboardInterrupt` (the existing token) and re-raising. `record_call` commits that row at once, so a later rollback in `run_arm`
  would not remove it.

## §7 Options for the ruling (each with what it records and what it costs; nothing decided here)

**1. The status on an interrupt.**
- **(S-a) Keep `failed`, reason `KeyboardInterrupt`.**
  - Records: an operator stop reads the same as a run that broke. A reader of the run table cannot tell them apart except by the reason
    string.
  - Costs: no test moves, and the entry's acceptance clause "closes `interrupted`" is not met (the entry would be amended).
- **(S-b) `interrupted`, reason `interrupt:SIGINT` / `:SIGTERM` / `:SIGHUP` (C47's form).**
  - Records: the same as the other two runners.
  - Costs: `run_arm` gains C47's `except (KeyboardInterrupt, rm.RunInterrupted)` before its `failed` branch, and `main` gains
    `rm.interrupt_signals()` and the `128 + signum` return; `exit_process` at `__main__` is optional, since the cloud path has no executor
    worker to abandon.
  - The test pinning `failed` changes (`test_failed_close_reason.py:146`), superseded.
- **Resume either way.** It reads `cloud_extractions` only, so the status changes nothing for resume.

**2. Where the rollback sits.**
- **(R-a) In `run_arm`, before the close**, C47's form: roll back if a transaction is open, then `is_closed`, then close.
  - Covers every point in Q2, rows 7–9 and 12 included.
  - Costs: row 4's uncommitted `run_calls` INSERT is dropped too, so a call that was made loses its row.
- **(R-b) In `store_result`**, for any exit (`except BaseException`).
  - Covers rows 7–9, but not row 12 (a close interrupted mid-commit), and leaves `run_arm` committing anything else that is open.
- **(R-c) Both.** The store cleans its own transaction, and the runner covers what is left.

**3. Whether an interrupted provider call is recorded.**
- **(P-a) No**, as now: the run's record undercounts by at most one call per interrupt.
- **(P-b) Yes:** `send` catches `BaseException` too, records `error` with detail `KeyboardInterrupt` / `RunInterrupted: SIGTERM`, and
  re-raises. It reverses R800(b)'s exclusion for interrupts. The row commits at once, so it survives R-a's rollback.

**4. SIGTERM and SIGHUP.** Without `rm.interrupt_signals()` in the cloud main, a tmux kill or closed terminal leaves the manifest open. S-b
needs it; under S-a it can still be added so the run closes at all.

**5. The row's first half.** No activation is owed (Q5). Close the half as answered, with the note that `legacy_record` filters by
`expected`. N46's legacy-table half stays where it is.

**6. Files touched**, under S-b with R-a or R-c:
- `scripts/run_cloud_extraction.py` (`run_arm`'s handlers, `main`'s signals and exit code);
- `engine/cloud/base.py` (only under R-b, R-c or P-b);
- the docs lines that state how a cloud run closes.

No schema change; the status token exists.

**7. Tests that move.** `tests/test_failed_close_reason.py`'s cloud interrupt test, superseded under S-b. Its two neighbours keep their
assertions. Any test that asserts the cloud run's close or `store_result`'s rollback, per census (e).

**8. The acceptance test's shape and seams.** `run_arm` itself on a scratch review, as §5 drives it: the real transport with a placeholder
key and a fake SDK class, a connection wrapper that raises at the first span INSERT. Asserted:
- no `cloud_extractions` or span row survives for the paper;
- the paper is still pending;
- the run closes with the ruled status and reason.

A second case: an interrupt inside the writer's savepoint (§5 (C)) leaves nothing. A third, under P-b: an interrupted provider call has its
`error` row. Each fails on the unmodified tree: §5 shows (A) and (C) commit rows and close `failed`.

**9. What U30 does not fix.**
- N46's unexpected spans in the legacy table (with U28's carry; P1).
- A15's per-arm axis.
- INT-ae12-2's retry budget.
- A second signal arriving inside an interrupt handler's `close_run` (the L04 reader's note at `:164`), which applies equally to the other

## §8 Findings

- **F1.** A cloud interrupt commits partial work: rows 7–9 of Q2's table, two of them driven (FAKE (A), (C)). (C) is not in the row's text:
  an interrupt inside the event writer leaves the legacy rows committed with no claims, and the paper done.
- **F2.** SIGTERM and SIGHUP have no handler on the cloud entry point, so they leave the manifest open with no end (Q4). C47 covered
  `run_pipeline` and the FT CLI only.
- **F3.** `run_arm`'s comment cites R625(a)(8) for closing `failed` on an interrupt (`run_cloud_extraction.py:122–123`). R625(a)(8) rules the
  reason form only, and the pinning test's own docstring says the cloud runner simply has no interrupt handling.
- **F4.** R798(e)'s "enforce_completeness already refuses unknown and missing names" is true for missing names and not for unknown ones.
  Those are logged as dropped and still inserted into the legacy table (`completeness.py:212–215`, `base.py:461`; N46). Claims are safe,
  because `legacy_record` iterates `expected`.
- **F5.** A KeyboardInterrupt during a provider call leaves a call that may have been transmitted with no `run_calls` row (Q2 row 2). It is
  the one gap left in U29's "every call has its row" inside a run.
- **F6.** An interrupt between `close_run`'s UPDATE and its commit leaves the manifest open, because `extractor.close()` discards the
  uncommitted close (Q2 row 12). C47's `is_closed` check after a rollback is the existing answer on the other runners.

## §9 What could not be established read-only

- Whether a real provider call interrupted mid-request was received and billed. Unknown from the client side; the probe raises before or
  instead of the call.
- The exact moment SIGINT lands inside the SDK's blocking socket read. Python delivers KeyboardInterrupt between bytecodes; the probe raises
