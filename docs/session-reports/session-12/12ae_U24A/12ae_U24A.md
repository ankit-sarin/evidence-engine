## §3 Mechanism at HEAD (3b)

1. **What the probe sends** (CODE ORDER). `check_model` resolves its request with `cfg = stage_config("preflight", spec, model=model_name)` (`ollama_preflight.py:66`) and sends it with `ollama_chat(messages=[dict(m) for m in PREFLIGHT_MESSAGES], max_retries=0, wall_timeout=60.0, **cfg.kwargs())` (`:69–74`). `kwargs()` returns `{"stage": self.stage, "model": self.model, "options": dict(self.options)}` plus `keep_alive` when sent (`effective_config.py:131–138`). `stage` is consumed by `ollama_chat` (`ollama_client.py:637` `stage: str | None = None,`) and never sent. The request `ollama_chat` builds is `request = {"model": model, "messages": messages, **kwargs}` (`ollama_client.py:713`).
2. **How each value resolves** (CODE ORDER). The preflight branch of `stage_config` (`effective_config.py:367–373`) reads `blk_src, blk = _block(spec, "preflight", PreflightConfig)` and sets `options["temperature"]` from `blk.temperature` and `options["num_predict"]` from `blk.num_predict`. `keep_alive` comes from `_keep_alive(spec)`, which reads `_block(spec, "ollama", OllamaRuntime)` (`:266–268`). `_block` returns the spec model's declared defaults when `spec is None`: `blk = getattr(spec, attr, None) if spec is not None else None` / `if blk is None: return None, cls()` (`:224–226`). The defaults are `review_spec.py:693–697` (`temperature: Temperature = Field(default=0)`, `num_predict: int = Field(default=4, ge=1)`) and `OllamaRuntime.keep_alive` `default=-1` (`:675–676`). The model is the caller's (`:377–378` `if model is not None: chosen, sources["model"] = model, "caller"`). So with `spec=None` the probe always sends `{"temperature": 0, "num_predict": 4}` and `keep_alive=-1`, whatever the run's spec says.
3. **Where the run's preflight row comes from** (CODE ORDER). `open_run` passes `preflight_models=` to `resolve_run` (`run_manifest.py:604–609`). `resolve_run` writes one entry per probed model, `cfg = stage_config("preflight", spec, model=m)` / `out[f"preflight:{m}"] = ResolvedStage(cfg, _digest(m), prompt_hash("preflight", spec, cfg))` (`effective_config.py:521–525`), **with the spec**. The row's `options_json` and `options_hash` are written from that resolution (`run_manifest.py:701–706`). Its callers: `run_pipeline._open_run_manifest` (`run_pipeline.py:535–556`, declaring the abstract primary's, the extraction model's and the auditor's probe) and `ft_screener.open_screening_manifest` (`ft_screener.py:569–582`, declaring both FT models when `with_preflight`). On a loaded spec the blocks always exist through `default_factory`, so the row's sources read `spec` even when the YAML omits the block (`_src(blk_src, …)` with `blk_src` the instance). That is a reading for question 5 of §1 2e.
4. **What refuses at the send** (CODE ORDER). Under an active run `ollama_chat` calls `check_declared_call(stage, model)` and then `check_call_digest(stage, model)` before the send (`ollama_client.py:759–764`). `check_declared_call` reads only the row's model: `row = conn.execute("SELECT model_name FROM run_stage_configs WHERE run_id = ? AND stage = ?", (run_id, key)).fetchone()` / `if declared != model: raise UndeclaredCall(key, declared, model)` (`run_manifest.py:1127–1131`). `check_call_digest` compares the digest only (`:1155–1164`). `grep -n options_hash engine/utils/ollama_client.py` returns nothing. **So a spec-less probe under an active run is not refused.** It sends options and `keep_alive` that may differ from its row, and nothing compares them. The one reader of a row's options at call time, `active_stage_row` (`run_manifest.py:821–834`), serves `EffectiveConfig.with_options`, which the probe does not use.
5. **What the run records of the probe** (CODE ORDER). `record_active_ollama_call` writes a `run_calls` row under the key `preflight:<model>` (`call_stage_key`, `run_manifest.py:1108–1111`; `:1187–1193`), with `request_hash=req_hash` computed once over the request as sent (`ollama_client.py:717` `req_hash = _compute_request_hash(request)`, `:728–730`). So under a non-default spec, `run_calls.request_hash` hashes the spec-less options while `run_stage_configs.options_hash` for the same key hashes the spec's. The inconsistency is recorded but never detected.
6. **The divergence, shown** (FAKE, §5). Under a spec with `preflight: {num_predict: 7, temperature: 0.5}`, S1, S2 and S3 send `{"temperature": 0, "num_predict": 4}` with `keep_alive -1`, while `stage_config("preflight", spec, model=m)`, the row's resolution, gives `{"temperature": 0.5, "num_predict": 7}`. Under `ollama: {keep_alive: "5m"}` they send `-1` against the row's `"5m"`. The extractor-form control (spec passed) sends the row's values in every variant.
7. **The pins** (CODE ORDER). "Not affecting" (R1) holds by the request path. The probe's stage is `preflight`, which is not among the extraction stages. The pinned tuples are the arms' extraction-stage resolutions (`12l_U04/pin_tuples.py`, both pins recorded at `12ad_close/pin_tuples_close.json`), and the audit `prompt_hash` is the `audit` stage's. Changing the probe's options moves none of them. A spec that *declares* a `preflight` block changes the spec's whole-file hash and the preflight rows, not an arm's pinned tuple.
