## The answer

On the cloud path an unexpected field name is logged as dropped and then written anyway. `store_result` calls `enforce_completeness`
and never `drop_unexpected`, so the extra span reaches `cloud_evidence_spans` and the raw response in `cloud_extractions.extracted_data`.
It never reaches the claims, because `legacy_record` builds them from the expected names only (FAKE §5 (A)).

A second effect the record does not name: the extra span also goes through the citation guard. If it is uncited, the whole paper is
refused, while the log line still says the field was dropped (FAKE §5 (B)). The local path drops the name first and stores the paper.

No reader on a run or export path changes its output. Three analysis readers that take every row do: the provenance census, the
judge-provenance span count and the span-loss autopsy (§4, FAKE §5).

## §2 Q1 — The write

**Where the expected names come from** (CODE ORDER). Both paths take them from the spec, cross-checked against the codebook, by one
function: cloud `self.expected_fields = expected_field_names(self.spec, self._review_dir / CODEBOOK_FILENAME)` (`engine/cloud/base.py:122`);
local `expected = expected_field_names(spec, cb_path)` (`engine/agents/extractor.py:665`).

**What `enforce_completeness` does with an unexpected name** (`engine/core/completeness.py:212–217`, CODE ORDER): `if result.unexpected:`
→ `logger.warning("Paper %d (%s): unexpected field(s) %s dropped (R118) — %s", …)` → `return result`. It drops nothing; the caller
must. `drop_unexpected` (`:220`) is that step: "R118: the spans whose field was asked for. An unexpected field is the response
inventing a field; it is dropped before any write, and `enforce_completeness` has already logged it."

**Every caller of `drop_unexpected`** (E1; census (f) and grep): `engine/agents/extractor.py:672` (`span_dicts = drop_unexpected(span_dicts,
expected)`, straight after `enforce_completeness` at `:671`), `:692` (the refusal's record), `:704` (the returned result); and one
test, `tests/test_completeness_guard.py:144`. None in `engine/cloud/`. The elicited path builds one span per codebook field ("for name
in order:", `engine/elicitation/pipeline.py:588`), so it cannot carry an unexpected name.

**The cloud path, in order** (CODE ORDER):
1. The transport parses the response whole: `extracted_data = json.loads(content)` (`openai_extractor.py:107`; Anthropic `:106`), then
   `spans = self.parse_response_to_spans(extracted_data)` (`:127`; `:132`). The parser validates shape (`ExtractionOutput`), not names.
2. `extract_with_completeness` checks `check_completeness(spans, self.expected_fields)` (`base.py:534`): an extra name leaves the result
   complete, so it is accepted on attempt 1 and its telemetry row records `spans_parsed=len(spans)` (`:548`), the extra one counted.
3. `store_result`: `enforce_completeness(spans, self.expected_fields, …)` (`:422`) logs the name as dropped; `enforce_citations(spans, …,
   mode=LEGACY, …)` (`:433`) then checks every span, the extra one included.
4. `INSERT INTO cloud_extractions` (`:444`) with `json.dumps(extracted_data)` (`:452`): the response verbatim, the extra name in it.
5. `for span in spans:` (`:461`) → `INSERT INTO cloud_evidence_spans` (`:463`): every span, the extra one included.
6. `write_extraction_events(self._conn, legacy_record(…, expected=tuple(self.expected_fields), spans=spans, …))` (`:485`, `:492`):
   `legacy_record` iterates `for name in expected:` (`engine/core/extraction_events.py:304`), so the extra span makes no claim.
7. `self._conn.commit()` (`:500`).

**The local path, beside it** (CODE ORDER): `enforce_completeness(span_dicts, expected, …)` (`extractor.py:671`) logs; `span_dicts =
drop_unexpected(span_dicts, expected)` (`:672`) drops; `enforce_citations(span_dicts, …)` (`:684`) checks the remainder; the claims
are written from `legacy_record(…, expected=expected, spans=span_dicts, …)`. The local path writes no legacy table (9b-FLIP, R111).
`tests/test_extraction_events.py:256` pins it with an uncited `Title` span (`source_snippet=""`): the paper stores, the name is
absent from the result and the record, and the log says "dropped".

## §6 Q5 — U30's seam

R805(d)'s design touches `store_result` (a rollback on any exit that did not commit), `run_arm`, `send` and the cloud `main`.

**Where a fix would sit** (CODE ORDER).
- **In `store_result`, after `enforce_completeness` (`base.py:422`) and before `enforce_citations` (`:433`)**: the local path's order
  (`extractor.py:671–672`). It is before every INSERT, so it is inside the transaction R805(d)(2)'s rollback covers. It reaches
  `cloud_evidence_spans` and the citation guard's input.
- **Earlier, in `extract_with_completeness` or `parse_response_to_spans`**: it would also change the telemetry row's `spans_parsed`
  (`:548`). If it ran before `store_result`'s `enforce_completeness`, the "dropped (R118)" line would no longer be logged, because the
  guard would never see the name.

**What dropping changes and does not** (CODE ORDER, FAKE where stated).
- No request byte. The request is built and sent, and its hash recorded, before the response exists (`send`, U29).
- No arm pin and no manifest value. The resolved tuple carries no response content.
- No claim and no claim hash. `legacy_record` already reads only the expected names, and FAKE (A) and (C) write the same 20 events.
- `extracted_data`. Unchanged by a span drop: `json.dumps(extracted_data)` (`base.py:452`) is the response, not the spans.
  SPANLOSS-01 reads it as the model's verbatim response ("So `extracted_data` *is* the model's response", `SPANLOSS-01_report.md:50`).
- `cloud_evidence_spans`. One row fewer per unexpected name.
- Case (B). The paper would store where today it is refused.

**Tests that pin today's behaviour** (census (f): 48 test functions coupled to the seam). None stores through the cloud path with an
unexpected name: the one coupled test that carries an extra name is local
(`tests/test_completeness_guard.py:122 test_unexpected_fields_are_dropped_and_duplicates_are_retryable`, extra names `Title`, `junk`).
The local pins of R118 are `tests/test_extraction_events.py:256` (t5) and `tests/test_terminal_states.py:134` ("an unexpected field no
longer refuses the paper"). A drop in `store_result` moves no existing test. A refusal moves none on the cloud side either, but it
gives the two paths different policies for the same R118 case.

## §7 Options for the ruling (each with what it records and what it costs; nothing decided here)

**1. (D) Drop before any write, as R118's docstring states.** `spans = drop_unexpected(spans, self.expected_fields)` after
`enforce_completeness` in `store_result`, as `extractor.py:672` does.
- Records: `cloud_evidence_spans` holds exactly the codebook names the claims hold. The log line becomes true. `extracted_data` keeps
  the response verbatim, the name in it.
- Costs: one line in `engine/cloud/base.py`, a file U30 already touches. Case (B) changes: an uncited extra span no longer costs the
  paper. The two paths then share R118's policy.
- **(D′) Also filter `extracted_data`.** This would stop rows 14–15 of §3 re-inserting the name. But `extracted_data` would then no
  longer be the response, which SPANLOSS-01's method relies on.

**2. (X) Refuse the response.**
- Where:
  - **In `store_result`**: the paper is failed after the provider call, with no re-ask, because `extract_with_completeness`'s check has
    already passed (L12-C10's pattern for duplicates). The paper stays pending and is re-asked on the next run.
  - **In `extract_with_completeness`'s check**: the response is re-asked under the one budget, costing up to its attempts in provider
    calls.
- Records: no row at all for the response, so `extracted_data` is never written.
- Costs: the cloud path refuses what R118 and the local path accept, which is two policies for one case; R118 would need amending for
  the cloud path.

**3. The acceptance test's shape.** `run_arm` on a scratch review, as §5 drives it, the response the codebook's 20 fields plus one
`invented_field`.
- Under (D), asserted: `cloud_evidence_spans` for the paper holds exactly the codebook names; the claims are unchanged (20 events, none
  outside the codebook); `extracted_data` still carries the name; the "dropped (R118)" line is logged.
- A second case, the extra span uncited (§5 (B)): under (D) the paper stores; under (X) nothing is stored.
- Each fails on the unmodified tree. FAKE (A) shows 21 span rows with `invented_field` among them, and (B) shows the paper refused.

**4. What N46 would still leave open.**
- Any rows already on live with a name outside the codebook (§4: not established).
- The two repair scripts' own insert path from `extracted_data` (§3 rows 14–15), recorded on C28 by R794 as not U28's.
- A duplicated field on the cloud path still fails the paper after the budget (L12-C10).
