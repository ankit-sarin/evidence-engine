## The blocking answer

U29 can be built on the existing schema and in `engine/cloud/base.py` for its first and third claims. Its second claim needs a decision
first, because none of the six outcome tokens describes it.

- **A send that raises.** `send` records only after `_create` returns (`base.py:153` `response = self._create(**payload)`, then `:154`
  `if self.run_id is not None:`). An exception from `_create` passes straight through, so no `run_calls` row is written (FAKE §5 (1): three
  raises, `run_calls rows: []`). U40's chain still keeps the hash, because it is appended before the call (`base.py:148–151`). The
  existing token `error`, with the exception named in `outcome_detail`, fits this case exactly as `ollama_chat`'s outer handler uses it
  (`ollama_client.py:871` `_record("error", exc=exc, note=…)`). This needs no schema change.
- **A truncated or refused response.** `send` returns the raw response and records `completed` (`base.py:161`). The finish reason is first
  read by the caller, after `send` has returned (`openai_extractor.py:59`, `anthropic_extractor.py:59`). The six tokens are
  `"completed", "refused_input_overflow", "refused_ceiling_unavailable", "refused_input_truncated", "refused_input_dropped", "error"`
  (`022_run_kinds_and_audit_tables.py:138–141`). Each `refused_*` token names a refusal of the INPUT by the local runtime's fit checks; none
  names a provider's truncated output or a provider's refusal. So the acceptance test's "a truncated response is not recorded completed"
  can only be met with `error` and a detail (R745(d)'s precedent: "A refused completed call is recorded with outcome 'error' and a detail
  naming the mismatch; no outcome is added (022's CHECK)"). The alternative is a new token, which is migration 023's (R745(d)), not U29's.
  The ruling has to choose.
- **The response digest.** It is NULL on every cloud row (`base.py:160` passes `None`). `rm.response_digest(content, thinking)`
  (`run_manifest.py:1028–1029`) can digest the text a cloud response carries, and that digest is stable across two answers identical in
  content. A digest of the whole response object is not stable: `id`, `created` and `usage` differ between two such answers (FAKE §5 (3)).
- **N47.** Both SDKs default to `max_retries = 2` (`openai/_constants.py:10`, `anthropic/_constants.py:10`), and both clients are
  constructed with the key only (`openai_extractor.py:37`, `anthropic_extractor.py:38`). So one `_create`, and so one recorded call, can be
  up to three HTTP sends.

## §3 Q2–Q6

### Q2 — Truncated and refused

**Where each transport learns the finish reason** (CODE ORDER). Both learn it after `send` returns, inside `extract_paper`:
- OpenAI: `openai_extractor.py:52` `response = self.send(paper_id, prompt)`, then `:59` `finish_reason = getattr(choice, "finish_reason",
  None)`.
- Anthropic: `anthropic_extractor.py:55` `response = self.send(paper_id, prompt)`, then `:59` `stop_reason = getattr(response,
  "stop_reason", None)`.

`extract_paper` returns the reason as `"finish_reason"`. Its one reader is `extract_with_completeness`, which writes it to the JSONL
telemetry row (`base.py:496` `finish_reason=result.get("finish_reason")`) and nowhere else.

**The values the SDKs declare** (installed source):
- OpenAI: `finish_reason: Literal["stop", "length", "tool_calls", "content_filter", "function_call"]`
  (`openai/types/chat/chat_completion.py:25`). A refusal is also carried as text in `ChatCompletionMessage.refusal: Optional[str]`
  (`openai/types/chat/chat_completion_message.py:63`). Nothing in the engine reads `.refusal` (`grep -n "refusal" engine/cloud/*.py`:
  no hit).
- Anthropic: `StopReason: TypeAlias = Literal["end_turn", "max_tokens", "stop_sequence", "tool_use", "pause_turn", "refusal"]`
  (`anthropic/types/stop_reason.py:7`).

**Whether `send` can know it.** `send` holds the response object (`base.py:153`), but it is provider-neutral: the two responses carry the
reason in different places (`choices[0].finish_reason` and `.message.refusal`, against `.stop_reason`). For `send` to record the case,
each transport would have to supply a small accessor that `send` calls before recording. That places the transports among U29's files,
as its entry lists them. Otherwise the caller, `extract_paper`, would have to record after `send` has already written the row, which means
an UPDATE of a row or a second row for one call. Neither exists today.

**Which token fits.** None names a provider-truncated or provider-refused output. The `refused_*` tokens name the local runtime's input
checks (§2's table). `completed` is what the local path writes for an output-length stop. `error` with a detail is R745(d)'s form for "a
refused completed call". **No existing token says "truncated" or "refused by the provider" in itself; a distinct token is a schema change
and 023's (R745(d)), not U29's.**

### Q3 — The response digest

**The local digest**: `rm.response_digest(content, thinking)` = `sha256_canonical({"content": content or "", "thinking": thinking or ""})`
(`run_manifest.py:1028–1029`), over the message's content and thinking (`:1190–1191`).

**What each SDK response offers to hash** (installed source): both response types are the SDKs' pydantic models, with `to_dict()` and
`to_json()` (`openai/_models.py:139`, `:177`; `anthropic/_models.py:129`, `:167`) and pydantic's `model_dump` / `model_dump_json`.
- OpenAI `ChatCompletion` carries `id`, `choices`, `created`, `model`, `object`, `service_tier`, `system_fingerprint`, `usage`
  (`chat_completion.py:50–68…`). The text is `choices[0].message.content`. `reasoning_content` is read by `getattr` at
  `openai_extractor.py:63–64`; it is not a declared field of the pinned type.
- Anthropic `Message` carries `id`, `container`, `content`, `model`, `role`, `stop_reason`, `stop_sequence`, `type`, `usage`
  (`anthropic/types/message.py:17–108`). `content` is a list of blocks: `text`, and `thinking` with a `signature`.

**What varies between two identical answers** (FAKE §5 (3)): for OpenAI, `fields that differ: ['created', 'id', 'usage']`, so `to_json()`
sha256 is not equal. For Anthropic, `['id', 'usage']`, also not equal. A content-only digest is equal in both: `rm.response_digest(message.content)
equal True` and `content blocks' model_dump equal True`.

**The options:**
- **(D1)** `rm.response_digest(text, thinking)`, the local function. OpenAI: text = `message.content`, thinking = the reasoning content when
  present. Anthropic: text = the joined `text` blocks, thinking = the joined `thinking` blocks. It is stable across identical answers,
  comparable in form with the local rows, and ties a stored result to its content. It does not tie it to one specific response.
- **(D2)** sha256 of `to_json()`. It is unique per response, but it varies with `id`, `created` and `usage`, so two identical answers
  differ, and it hashes metadata the engine never stores.
- **(D3)** D1, plus the provider's response `id` in `outcome_detail`. Identity without unstable hashing.

### Q4 — N47

**Read from the installed packages:**
- **Defaults.** openai 2.24.0: `DEFAULT_MAX_RETRIES = 2` and `DEFAULT_TIMEOUT = httpx.Timeout(timeout=600, connect=5.0)`
  (`openai/_constants.py:9–10`). anthropic 0.84.0: `DEFAULT_MAX_RETRIES = 2` and `DEFAULT_TIMEOUT = httpx.Timeout(timeout=10 * 60,
  connect=5.0)` (`anthropic/_constants.py:9–10`). Both clients take `max_retries: int = DEFAULT_MAX_RETRIES` in their constructor
  (`openai/_client.py:111`; `anthropic/_client.py:69`).
- **What they retry on.** Each client's request loop retries on `httpx.TimeoutException` and on any other `Exception` from the transport
  send, while retries remain (`openai/_base_client.py:1010–1037`; `anthropic/_base_client.py:1077–1104`). On an HTTP error status it
  retries when `_should_retry` says so: header `x-should-retry: true`, or status 408, 409, 429 or ≥ 500 (`openai/_base_client.py:773–806`,
  `:1054`; `anthropic/_base_client.py:799–832`, `:1121`). Each retry carries `x-stainless-retry-count` (`openai/_base_client.py:452–453`;
  `anthropic/_base_client.py:463–464`).
- **A send-side refusal (Anthropic).** For a non-streaming request whose `max_tokens` implies more than 10 minutes, Anthropic raises
  `ValueError("Streaming is required …")` before any send (`anthropic/_base_client.py:726–735`, called from
  `resources/messages/messages.py:978`). The live arm's `max_tokens` 16000 gives 3600 × 16000 / 128000 = 450 s, under the 600 s limit
  (computed by hand from that formula; INFERRED).
- **Where the clients are constructed.** `engine/cloud/openai_extractor.py:37` `self.client = openai.OpenAI(api_key=key)` and
  `engine/cloud/anthropic_extractor.py:38` `self.client = anthropic.Anthropic(api_key=key)`, the key only (census (c): the only two
  constructions in `engine/`, `scripts/`, `analysis/` and `tests/`).

**So one `_create` can be up to three HTTP sends**, with one hash and, today, at most one `run_calls` row.

**The options:**
- **(N-a)** `max_retries=0` at construction, in both transports. One recorded call is then one send, and the retrying stays where the
  engine already does it: the transports' own three-attempt loops (`openai_extractor.py:147ff`, `anthropic_extractor.py:170ff`), each
  attempt a `send`, so each a row. Cost:
  - two transport lines;
  - the SDK's own backoff on 408/409/5xx goes away, leaving the transports' fixed 2 s / 4 s waits and their 30 s+ backoff for 429;
  - U27's test asserts the constructor's keywords are exactly `{"api_key": PLACEHOLDER_KEY}` (`tests/test_u27_cloud_run_faults.py:219`),
    a coupled test.
- **(N-b)** Keep the default and record the count. The SDK puts no retry count on the returned model. `retries_taken` is internal to
  `_base_client` and visible only through the raw-response wrapper, so this needs `with_raw_response` in each `_create`. That is more code
  in both transports, and it changes what `_create` returns.
- **(N-c)** Keep the default and say so in `outcome_detail`: no change to what is counted.

### Q5 — Where the record goes

**Which exceptions can reach `send`.** The two SDKs raise:
- `APIConnectionError`, with `APITimeoutError` its subclass (`openai/_base_client.py:1023`, `:1037`; anthropic at `:1090`, `:1104`);
- the `APIStatusError` family by status: `BadRequestError` 400, `AuthenticationError` 401, `PermissionDeniedError` 403, `NotFoundError`
  404, `ConflictError` 409, `UnprocessableEntityError` 422, `RateLimitError` 429, `InternalServerError` ≥ 500, each raised once retries
  are spent;
- Anthropic's `ValueError` before any send (Q4);
- and anything a fake or a client-side defect raises (`TypeError` on a bad keyword).

Each would carry `error`, with `f"{type(exc).__name__}: {exc}"` in the detail, as `_record` forms it (`ollama_client.py:725–727`). That
form distinguishes them without a new token. "Raised before transmission" cannot be told from "after" by class in general:
`APIConnectionError` can mean the connection never opened.

**If the recorder itself raises while an exception is in flight.** `record_call` does an INSERT and a commit on `self._conn`
(`run_manifest.py:1053–1058`). A `sqlite3.Error` there is a run fault: `sqlite3.Error` is the first entry of the tuple
(`extraction_events.py:468–474`), and both transports' handlers `raise` on `is_run_fault(exc)`.
- **Recorded inside an `except` around `_create`, then re-raised:** a recorder fault replaces the provider exception. It propagates, with
  the provider error as `__context__`, and the run closes `failed` with the recorder's reason, which is U27's behaviour for a recorder
  fault after success. This is the closer match to `ollama_chat`, whose outer `_record("error", …)` sits in an `except` (`:870–871`).
- **Recorded in a `finally`:** the same in effect.
- **A recorder failure swallowed so the provider error survives:** a run that cannot record would continue. That contradicts R216's "the
  recorder runs on every path".

**What U40's chain holds for a raised send.** The hash, appended before `_create` (`base.py:148–151`). FAKE §5 (1):
`chain: paper 1, 2 hash(es)` after two raises on paper 1, with `run_calls rows: []`. So today a claim stored after a raise-then-succeed
sequence carries, in `context_chain`, a hash with no `run_calls` row. U29's error row closes that gap: every hash in a chain would then
have a row (F3).

**What the transports must change.**
- For claim 1 (raise) and claim 3 (digest): base.py alone suffices, provided the digest's text is reachable from base. It is not uniform:
  OpenAI's text is `choices[0].message.content`, Anthropic's is the `text` blocks. A provider-neutral digest needs a transport accessor,
  or `send` branching on `PROVIDER`.
- For claim 2 (truncated/refused): a transport accessor for the finish reason.
- For N-a: the two constructor lines.

So the entry's three files stand.

**U27's test moves under claim 1**: its provider-route paper-outcome cases assert `calls == 0` (`tests/test_u27_cloud_run_faults.py:214`).
With an error row per raised send, those cases write six rows, so the test is coupled.

## §7 Options for the ruling

1. **Where the record is written.** In `send`: `try: response = self._create(**payload)`, and on an `except BaseException` (or
   `Exception`; see 6), under a run, `record_call(…, None, …, outcome="error", outcome_detail=f"{type(exc).__name__}: {exc}")`, then a bare
   `raise`. The completed record moves after the outcome and digest are computed. One site per outcome, as `ollama_chat`'s.
2. **The outcome per case**, with today's six tokens:

   | Case | Token |
   | --- | --- |
   | raised | `error` |
   | truncated | `error` + detail `finish_reason=length` / `stop_reason=max_tokens` |
   | refused | `error` + detail |
   | complete | `completed` |

## §8 Findings

- **F1.** No outcome token names a provider-truncated or provider-refused output. All four `refused_*` tokens name the local runtime's input
  checks (`022…py:138–141`; `ollama_client.py:744`, `:747`, `:770`, `:773`). The entry's second clause therefore resolves to `error`
  plus a detail under R745(d), or to 023.
- **F2.** The local path records an output-length stop as `completed`: `_finish` checks only that the input was read
  (`ollama_client.py:742–753`). If U29 records a cloud truncation as `error`, the two paths read the same event differently. That is the
  ruling's to accept or align.
- **F3.** Since U40, a stored claim's `context_chain` can name a hash with no `run_calls` row: the hash of a send that raised before a later
  attempt succeeded (`base.py:148–151` before `:153`; FAKE §5 (1)). U29's error row makes every chained hash recorded.
- **F4.** OpenAI's refusal text, `ChatCompletionMessage.refusal` (`openai/types/chat/chat_completion_message.py:63`), is read nowhere in the
  engine. A refusal is visible only as `finish_reason` `content_filter` when the provider sets it, and as zero spans.
- **F5.** `rm.record_call` commits the connection it is given (`run_manifest.py:1058`). On the cloud path that is `self._conn`, the
  connection `store_result` later uses. A record written inside a store's transaction would commit it early. Today no `send` happens
  inside a store, so this is a constraint on the build, not a defect.
- **F6.** `tests/test_run_manifest.py`'s C16 test fakes the provider with `return "response"` (`:385`). An accessor reading the finish
  reason from the response breaks it unless the accessor tolerates a non-response. That is a coupled test for the build.
- **F7.** The census's (d) list of tests naming `record_call` is all the telemetry function. The two functions share a name (R4), so a
  text search for the cloud recorder over-counts. The AST census resolves each call by its import.

## §9 What could not be established read-only

  `content_filter` or `stop` with `.refusal` set): the probe uses the SDK types' declared fields, not provider responses.
- Whether a live provider honours `max_retries=0` in every path (e.g. Anthropic's 529 "overloaded"): read from `_should_retry` only.
- Which exception classes arise in practice under the live network: §3 Q5 lists what the SDK source can raise.
