# 12af-U40A — U40's Phase A read-out: the cloud path writes claim events (B9, C28; Wave 2 row 25)

## The blocking answer first: A1 is not one change in `store_result`

**The engine's writer, `write_extraction_events`, accepts a cloud write once three inputs that `store_result` does not hold are supplied.** It always writes one paper-level processing event as well as the claims. `paper_events` has no arm column, so that event moves the paper's single processing axis, which the local pipeline reads. A1 as "call the local writer in `store_result`" therefore changes what the local audit, the workflow gate, PRISMA, the pipeline stats and every export's processing columns report. It also drags other files with it.

- **The three missing inputs.** `store_result`'s signature (`engine/cloud/base.py:324`) carries no `ParsedTextRef`, no request hash and no call chain. The writer refuses each absence:
  - (a) no text identity → `ClaimWithoutInputIdentity` (`engine/core/events.py:390`);
  - (b) no `presented_context_sha256` or an empty `context_chain` → `ClaimWithoutPresentedContext` (`events.py:394`);
  - (c) no `run_id` → `RunLinkRefused` (`events.py:240`).

  FAKE (`fake_probe_u40a.txt`, (ii)): all three refused, nothing written. The full form is accepted: "20 field events (['asserted']); paper event extracted -> extracted from None payload.arm=openai_o4_mini_2025_04_16_high".
- **The paper event.**
  - It is written by `write_paper_event(conn, **plan.paper_event, commit=False)` (`extraction_events.py:701`).
  - For a record: `rec, event_type="extracted", to_state="extracted", from_state=from_state` (`:661`).
  - For a failure: `payload={**dict(outcome.detail), "arm": outcome.arm}` with the failure's `to_state` (`:604`).
  - The arm lives only in the payload. `effective_state` reads `"… FROM paper_events WHERE paper_id = ? ORDER BY event_id"` (`effective.py:464`), and the last processing token wins whichever arm wrote it (`:481`).
- **What the FAKE shows on that axis** ((iii-a)):
  - A cloud store on a paper the local arm had audited returns it to `extracted`, holding `AI_AUDIT_COMPLETE_STAGE` pending.
  - A cloud `PaperFailure` turns a locally audited paper into `extraction_failed` / `model_call_failed`. PRISMA then counts it as a failure, not an included study.
  - The local audit writes `audited_ai` for the local arm, `located 0`, on **thirteen papers the local arm holds no claim on** — every paper only the cloud arm extracted.
- **The fix the FAKE confirms.** With the cloud arm's claims written, the gate does what the entry asks:
  - before: the gate skips and does not raise, `skip_reason='only 0 eligible papers hold a live claim …'` (E2 held);
  - after: `RAISED DistributionCollapseError: Distribution collapse detected in 1 field(s): study_type`.

So the trace is complete for the writer and the consumers. The design question it leaves is not "can the cloud path write claim events" but **whether a cloud write may write a paper-level processing event**. That needs the ruling (§7, options A1-α / A1-β).

### Transaction behaviour (CODE ORDER, then FAKE)

- **The writer:** `conn.execute("SAVEPOINT extraction_events")` (`:697`); every event with `commit=False`; `RELEASE`, then `if conn.in_transaction: conn.commit()` (`:704`). On any exception it runs `ROLLBACK TO extraction_events` (`:707`) and re-raises.
- **`store_result`:** its INSERTs run on `self._conn` (`base.py:109`, `isolation_level ''`, so an implicit transaction opens at the first INSERT), then `self._conn.commit()` (`:409`), or on exception `self._conn.rollback(); raise` (`:413`).
- **Called between the span INSERTs and that commit**, the writer's savepoint nests in `store_result`'s transaction. Its commit then commits both. A refusal rolls back to the savepoint, leaving the INSERTs pending for `store_result`'s own rollback. FAKE:
  - "INSERT pending (in_transaction=True), writer accepted: in_transaction after=False; the INSERT visible to a second connection: 1 (the writer's commit committed it)";
  - "INSERT pending (in_transaction=True); after the refusal in_transaction=True; visible to a second connection: 0", then "after store_result's own rollback: cloud_extractions rows for paper 16: 0".
- **One more path (CODE ORDER).** `write_field_event`'s INSERT block ends `except Exception: conn.rollback(); raise` (`events.py:497`). An INSERT-time failure, such as an FK on an unregistered arm, rolls back the whole outer transaction, cloud INSERTs included. The writer's `if conn.in_transaction:` guard then skips its `ROLLBACK TO`. The result is still all-or-nothing.
- **The connection works with the writer.** `self._conn` has `row_factory = sqlite3.Row` (`base.py:110`), and every reader the writer calls works on it (FAKE: the full form accepted on `base._conn`).
