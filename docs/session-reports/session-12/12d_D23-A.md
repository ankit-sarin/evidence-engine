## Q6. Today's mismatch behaviour, and the D22 interplay — READ

**Claims from v2, audit resolves v3, step by step:**

1. `claims = live_claim_events(conn, pid, arm, event_types=("asserted",))` — the v2 claims are live,
   so the paper is taken. Nothing reads their payload identity or `claim_inputs`.
2. `ref = resolve_parsed_text(conn, pid)` returns v3; `read_parsed_text(ref)` verifies v3's hash and
   succeeds. No refusal, no log line about the version.
3. Each claim: `locate(text, c.source_snippet)` against v3. A snippet quoted from v2 is located only
   if it survives into v3 exactly or above the fuzzy threshold (`located = best > threshold`).
4. A populated, unlocated claim with a snippet goes to `semantic_verify`: one model call that judges
   value against snippet (Q2). One with no snippet is `flagged` without a call.
5. Written in one savepoint:
   - `citation_located` per claim, `located` true or false, with `parsed_text_sha256` /
     `parsed_text_uid` **of v3**. The claim's own payload says v2. The two are comparable after the
     fact; nothing compares them.
   - `audit_verdicts` rows for step 4, with no text identity.
   - one `audited_ai` paper event, payload `"parsed_text_sha256": ref.sha256` (v3).
6. The claim is now in `done` on every later audit (`todo = [c for c in claims if c.claim_id not in
   done]`), so it is never located again, against any version.
7. The reader counts any located citation: `located = any(bool(c.get("located")) for c in
   citations)` (`classify_field_state`). It does not read the citation's text identity. A v2 claim
   whose snippet is absent from v3 reads as asserted without evidence; one whose snippet is present
   reads as asserted with evidence, on the strength of a text the model was not shown.

**The audit refusal branch (D22):**

```python
        except ParsedTextError as exc:
            logger.warning("Paper %d: audit skipped — %s (%s)", pid, exc.reason_code, exc)
            refused.append((pid, exc.reason_code))
            continue
```

Today it can carry three reasons, all about the **newest** version: `parsed_text_not_recorded`,
`parsed_text_missing`, `parsed_text_modified`.

**Refusal reasons that would exist if audit read the claim's own version:**

| condition | existing code that fits | note |
|---|---|---|
| the claim's version file is gone | `parsed_text_missing` | now about a superseded version, which nothing else reads |
| the claim's version file was edited | `parsed_text_modified` | same |
| the claim's `parsed_text_uid` names no `parsed_text_refs` row | none exactly; `parsed_text_not_recorded` means "the paper has no row at all" | append-only triggers make it unreachable by engine writes; no FK enforces it |
| the claim has no recorded identity (no `claim_inputs` row, no payload keys) | none | reachable only from a migration seed today; no such claim on live |
| a paper's `todo` claims span more than one version | none | the refusal becomes per claim or per version, while `skipped_refused` and the `audited_ai` payload are per paper |
| `parsed_text_not_recorded` for the paper | — | no longer reachable for a paper that holds an extractor claim |

So reading the claim's version moves D22's refusal from "one reason per paper" towards "one reason
per (paper, version)" and adds up to two conditions with no code today.

## Classification

D23 as stated — audit reads the newest version, not the claim's, and records no comparison — is:

- **(i) fixable in code with existing vocabulary and schema**, if the fix is "audit reads the claim's
  own version" and its refusals stay on the three existing parsed-text codes, or if the fix only
  records the comparison in `payload_json`;
- **(ii) needs a new reason code or constant**, if a version mismatch, an unresolvable uid or a
  claim without identity becomes a named refusal or skip;
- **(iii) needs migration 023** only where the chosen design writes an audit refusal as a
  `paper_events` row, which is the D22 ruling's question and not D23's own. No candidate below needs
  a new column for the text identity itself: the claim already stores it.

## Findings beyond the questions

- **F1 — `semantic_verify` never uses the paper text it is given** (READ; Q2). `paper_text` is a
  positional parameter with no use in the body; the verifier sees the snippet, the value and the
  field. Whether that is intended is not established by this read. Candidate row; not chased.
- **F2 — a partial re-extraction leaves stale claims live and unreachable** (READ; Q4 P1). After a
  re-parse, a field the new extraction leaves incomplete keeps its old-text claim live, and selection
  then skips the paper on the new key. The old-text claim is then the only live claim on that cell,
  so it is what `effective_value` resolves (`_classify_claim` was not read, so what its provenance
  says about the text is not stated here). This is a supersession/selection matter, wider than D23. Candidate row; not chased. No test
  for this case was found among the test names read (`tests/test_extraction_events.py::test_t9_…`
  covers full supersession).
- **F3 — `citation_located` has one write site** (grep of `citation_located` over `engine/`,
  `scripts/`, `analysis/`, `*.py`: the only `write_field_event(… event_type="citation_located" …)` is
  in `audit_run`; `engine/elicitation/pipeline.py` has no `locate(` call). R17's text says "The
  elicited path writes the located event at extraction time." Whether a later ruling superseded that
  clause was not checked. Reported, not chased.
- **F4 — `claim_inputs.parsed_text_uid` has no foreign key to `parsed_text_refs`** (MEASURED, DDL).
  Relevant to design A's "uid names no row" case.
- **F5 — the `audited_ai` payload stores the text's sha256 but not its uid, and `audit_verdicts`
  stores neither** (READ / MEASURED). Relevant to A and C.
- **F6 — P3: the reuse key ignores the uid**, so a byte-identical re-parse yields claims and
  citations that name different uids for the same bytes (READ). Benign for content; it matters to any
  design that compares by uid rather than by sha256.
