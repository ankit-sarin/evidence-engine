### W1-F4-C2 — The `failed` close commits whatever transaction the failing stage left open; only the interrupt close rolls back

- **File / function:** `scripts/run_pipeline.py::run_pipeline` (the `except Exception` and
  `except RunAborted` handlers) with `engine/core/run_manifest.py::close_run`.
- **Pattern:** iii (and i: the handler's own comment)
- **Evidence level:** reproduced
- **Evidence:**
  - `run_pipeline`: `except Exception as exc:` / `logger.error("Pipeline failed: %s", exc, exc_info=True)` /
    `_finish_review_run(db, run_id, "failed")` / `raise` — no rollback. The interrupt handler below it
    does roll back, and says why: `# … Roll back first, then check: an uncommitted write is never`
    `# committed by the close` → `if db._conn.in_transaction:` / `db._conn.rollback()`.

    stage's pending rows with it.
  - A real writer on the run's path that leaves a transaction open on error:
    `engine/core/database.py::add_papers` — a loop of `self._conn.execute("""INSERT INTO papers …""")`
    under `except sqlite3.IntegrityError: continue` only, with the single `self._conn.commit()`
    after the loop. Any other exception mid-batch exits with the earlier INSERTs pending.
  - Reproducer `~/scratch/12i-w1/repro/W1-F4/W1-F4_2_failed_close_commits_open_txn.py` (real

  unserialisable `authors`) cannot come through a validated `Citation`; the realistic triggers are
  a sqlite error after the first INSERT of a batch (I/O, disk full) — not established as observed.

  `failed` closes was not added" is about the reason text. Nothing found on the failed close and

### W1-F4-C3 — Every exit logs "PIPELINE COMPLETE", a gate stop exits 0, and the stats read in `finally` can replace the propagating exception

- **File / function:** `scripts/run_pipeline.py::run_pipeline` (`finally`), `::main`
- **Pattern:** i / other
- **Evidence level:** code order
- **Evidence:** `finally:` / `rm.deactivate(run_token)` / `elapsed = time.time() - t_start` /
  `stats = db.get_pipeline_stats()` / `logger.info("PIPELINE COMPLETE in %.1fs", elapsed)` /
  `logger.info("Pipeline stats: %s", json.dumps(stats, indent=2))` / `db.close()`. The two gate
  stops are `_finish_review_run(db, run_id, "interrupted", reason=rm.REASON_BLOCKED_…)` / `return`;
  `main`: `run_pipeline(…)` then `return 0`.
- **What goes wrong:** (a) a run that failed, aborted, was interrupted or stopped at a gate ends
  its log with "PIPELINE COMPLETE in …s"; (b) a BLOCKED run returns exit status 0 — the only
  machine-readable trace of the stop is the manifest's `end_status`; (c) `get_pipeline_stats()`
  runs one `effective_state` per paper in the database (every paper, not the corpus) inside
  `finally`: if it raises, that exception replaces the one in flight — including a
  `KeyboardInterrupt`/`RunInterrupted`, so `main`'s handler and its 128+signum exit are not
  reached — and `db.close()` is skipped.
- **Refutation tried:** the manifest close happens before `finally` on every path, so no stored
  state depends on it; (c) needs `get_pipeline_stats` to raise, which I did not establish (it would
  on a lock error or an event-store token the reader refuses). C40/C47 rule the manifest's end, not
  the log line or the exit status of a gate stop; grep of the plan for "PIPELINE COMPLETE": none.
- **Tests:** `tests/test_run_interrupts.py::test_t7_a_clean_main_exits_zero` pins 0 for a clean
  run; no test asserts the exit status of a gate stop, and none reads the final log line.
- **Existing row:** new
- **Proposed class / package:** 3 / P7 — log wording and exit status; no stored value involved.
