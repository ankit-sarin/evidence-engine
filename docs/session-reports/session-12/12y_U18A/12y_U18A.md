## §3 The digest, chat and preflight paths (3b–3d)

**Digest (3b).** One read per declared model, at run open: `open_run` → `resolve_run`
(`run_manifest.py:461`, `digest_fn=digest_fn`) → `_digest(model)` → `digest_fn(model)`
(`effective_config.py:516`), defaulting to `fetch_model_digest` with `base_url=OLLAMA_BASE_URL`. Production
callers of `open_run` pass `digest_fn=None`. `ft_screener.py:561/585`, `ft_screening_adjudicator.py:334/514`,
`import_screening_entry.py:136` and `import_extraction_entry.py:251` thread a `digest_fn` parameter through,
as a test seam. `open_review_session` passes `digest_fn=lambda m: ""` (`run_manifest.py:717`). The digest is
written to `run_stage_configs.model_digest` and pinned into `arms.configuration_json`. **Nothing on the run
path reads a digest from the server after `open_run`.** Every later use reads the manifest's stored value
(`rm.stage_digest(...)`: `extractor.py:1096`, `ft_screener.py:263`, `audit_events.py:155`), and those
values become each event's `actor_digest`. `tests/test_extraction_run_link.py:215`
`test_t5_the_extractor_names_no_digest_fetch` pins that the extractor names no fetch.

**Chat (3c).** Every engine model call is `ollama_chat` → `_client.chat` (H7), with `_client` as bound at
that moment: at import from `OLLAMA_HOST`, or by whoever rebinds it. The per-call check is
`check_declared_call` (`run_manifest.py`, called from `ollama_client.py:564`). It compares the model name
and nothing else:

```python
    row = conn.execute("SELECT model_name FROM run_stage_configs "
                       "WHERE run_id = ? AND stage = ?", (run_id, key)).fetchone()
    declared = None if row is None else row[0]
    if declared != model:
        raise UndeclaredCall(key, declared, model)
```

No host and no model digest is compared. `run_calls.digest` is the **response** digest
(`response_digest(content, thinking)` in `record_active_ollama_call`), not the model's. The Ollama chat
response names the model by tag only. R4 (Wave 1 row 16) holds at HEAD.

**Preflight (3d).** `require_preflight` → `check_ollama_env` (H9, the local unit) → `preflight_check` →
`check_model` → `ollama_chat` (H1, the probe generation, under the `preflight` stage) → `_get_model_vram_gb`
/ `preflight_check`'s VRAM sum through `ollama.ps()` (H8). The probe and the chat calls that follow share
H1. The VRAM figure comes from H8, which equals H1 only while nobody has rebound `_client`; the environment
check reads the local service whatever H1 is. **So a preflight can report one server's VRAM and the local
unit's environment while its probe and the run's calls go elsewhere** (finding 3).

## §9 What the Phase A could not establish read-only

- Whether `ollama pull` or `ollama create` on an open tag during a run changes the blob the running server

  the chat that follows uses it was not exercised (it needs a model load).
- The behaviour of a split host end to end (case i) against a second live server: stated from code, not run.
- Whether any operator or job sets `OLLAMA_HOST` for an engine process outside the shell, profile, crontab
  and service unit read here (for example a tmux environment, or another lane's wrapper).
- A per-call duration of an extraction call: none is recorded. §5's figure is derived from a stage total.
