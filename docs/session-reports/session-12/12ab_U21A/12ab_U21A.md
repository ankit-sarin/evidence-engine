## §3 Mechanism at HEAD (3b)

All CODE ORDER unless marked.

**A success.** The worker returns; `future.result` returns; the `else:` at `:779` runs `_finish(response)`, which checks the loaded context under a run (`:675`), checks the count, records `completed` once, and returns. The executor is not shut down (N24; also `:867` after a restart, which N24 does not name). `started_at` was taken at `:652`, before the first attempt, so a success on attempt 3 records the first attempt's start.

**A watchdog timeout.** `future.result` raises at `effective_timeout`. `except FuturesTimeoutError` at `:722` shuts the executor down with `wait=False, cancel_futures=True`, under the comment "Abandon the hung thread — do not wait for it" (`:723`). `cancel_futures` cancels only a pending future, and this one is running, so **the worker thread and its HTTP request survive**, bounded only by the read timeout. If attempts remain it sleeps `retry_delay` and the loop makes a new executor and sends again. If not, it calls `_restart_ollama_and_retry`.

**What the server is told when the client gives up: nothing.** No line closes a client, a connection or a request. `_client` is one module-level client (`:102`), shared. The abandoned worker holds its connection until a byte arrives or the read timeout fires. `ollama.Client` in 0.6.1 declares no `close` (`grep 'def close' .venv/.../ollama/_client.py` returns nothing); the httpx client behind it is `_client._client`.

**An HTTP timeout.** `httpx.ReadTimeout` is raised in the worker and re-raised by `future.result`. The arm at `:751` shuts down, logs "Ollama HTTP timeout", sleeps and retries; on the last attempt it re-raises at `:763`, with **no restart**, and `:791` records `error`.

**A connection refused.** `ollama/_client.py:134–135` turns `httpx.ConnectError` into the builtin `ConnectionError`, so the `httpx.ConnectError` half of `:751` does not fire for a chat (already row INT-i12-66). It reaches the arm at `:765`.

**A server error, or anything else.** `ollama.ResponseError` and others reach `:765`: same retry, then re-raise at `:777`, recorded `error`. An error response is retried like a hang.

**N23's race.** The two clocks start at different moments: the watchdog at `:720`, after `submit`; the read timeout when the worker begins its read, after connect and write. So at 32b the watchdog's deadline comes first by the connect and write time, and it ordinarily wins, but nothing orders them. **The race matters only on the last attempt:** before that both arms sleep and retry alike. On the last attempt the watchdog arm restarts the server and the HTTP arm re-raises. When the watchdog wins, the worker's `ReadTimeout` lands in a future nobody reads.

## §5 The acceptance test against HEAD (3d)

**Can it be written against HEAD's seams, and does it fail? Yes (FAKE).** `fake_seam_probe.py` replaces `oc._client` with a fake whose `chat` counts concurrent entries and blocks on an event. With `wall_timeout=0.2, retry_delay=0, max_retries=2` and the opt-out set:

elapsed 0.62s entries 3 peak concurrent 3 still in flight at the raise 3 threads 4

The assertion that fails on HEAD is the peak: `assert fake.peak == 1` reads 3. The seam exists (`_client`, patched 24 + 53 times by the census), and the fake must release its event before the test ends or process exit waits on the worker, which is the row's "process exit waited".

**"The recorded outcome distinguishes the four endings": what it requires of `run_calls`.** `run_calls.outcome` carries six tokens under a CHECK (`engine/migrations/022_run_kinds_and_audit_tables.py:138–141`, `:334`): `completed`, `refused_input_overflow`, `refused_ceiling_unavailable`, `refused_input_truncated`, `refused_input_dropped`, `error`. `outcome_detail` is `TEXT`, unconstrained (`:335`). At HEAD the four endings have one token and one identical detail text (§3).

- **Without a migration:** the four can be distinguished in `outcome_detail` under `error`, by surfacing the cause in the text `_record` writes (`:664`). Nothing reads `outcome` or `outcome_detail` in `engine/`, `scripts/` or `analysis/` (`grep` for `outcome` beside `run_calls`: only the writer), so no reader moves. Only tests do.
- **With a migration:** distinct tokens need the CHECK rebuilt, which is a table rebuild in a numbered migration. R745(d) already leaves "a distinct outcome" for "migration 023's to weigh", and `run_manifests.ollama_host` is owed to 023. The unit's Files list names `engine/migrations/`.
- **Which the test needs:** the entry's words are "the recorded outcome distinguishes". Read as the `outcome` column, that needs 023. Read as the outcome record, `outcome_detail` carries it now. **The code does not decide this; the ruling does.** Row 66's per-attempt count is a separate question: `run_calls` has no attempt column, nothing makes rows unique per call, and a second row per attempt needs no migration, only the T6-form pins moved.

**The restart itself:** a recovered call records `completed` with NULL detail, so "a run's manifest cannot show that the server was restarted mid-run" (W1-F5:90) stands on the success path too. ## §6 The cases (3e)

| Case | What HEAD does | What the row's fix says |
|---|---|---|
| Timeout, then retry, previous request still running | Abandons the thread, sends again after `retry_delay` (`:723–733`). Overlap at L < 900 by §3's table | No attempt starts while the previous one runs. "Timeout then wait", "then close" and "then stop" are §7's options |
| Timeout, then restart, then final attempt (F7) | The restart ends the server's work, whatever the abandoned threads are doing (not measured). Final send 10 s later, with no digest or environment re-check; a failure of any cause surfaces as `TimeoutError` | The send is not concurrent with a live request if the restart really ended it; F7's re-checks ride here (R734(e)). The row says nothing of a refused restart, where threads stay live and there is no further send |
| HTTP timeout racing the watchdog (N23) | At 32b, either arm; on the last attempt, restart or no restart by which fired first (§3) | N23 asks for one condition to log and route one way |
| 70b: read timeout before the watchdog (F3) | HTTP arm every attempt; the restart path never reached | Not named by the row or N23; same family |
| Success after a timeout | One `completed` row with the first attempt's `started_at`; the earlier abandoned generations leave no row | Row 66: uncounted. The acceptance test does not name it |
| The limit of attempts exhausted | Restart path (watchdog) or re-raise (HTTP, other); one `error` row | The four endings distinguished |
| `max_retries=0` (preflight, PDF quality) | The first watchdog timeout goes straight to the restart path (F5) | The row says nothing. A rule that waits or stops changes this path too |
| Interrupt during a wait | `future.result` raises in the caller; the worker runs on; no `_record` (the handler at `:785` takes `Exception`, not `BaseException`) | Not named. A longer wait makes it likelier |

## §7 Options (3f) and classified sites (3g)

The one design question: how "no attempt starts while the previous request is still running" is enforced. **Costs are for a real silent hang on the host's limits (ARITHMETIC).** **No recommendation:** the code does not make one option the only one, and the measurement bears on O2, O3 and on how O1's wait is read.

**O1 — Wait on the previous request's thread.** After the watchdog fires, `future.result()` again, bounded by the read timeout, before any retry.
- *Changes:* the three-line shape of each arm; the watchdog's limit becomes when the wait starts, not when the attempt ends.
- *Cost:* every attempt runs to `send + 900 s` on a silent hang. 8b goes from 960 s to about 2,760 s before the restart path (3 × 900 + 2 × 30); 27b from 1,860 s to the same; 32b unchanged.
- *What it doesn't settle:* the wait covers the client's thread. If the server is still generating after the client's read timeout, the next attempt can still overlap on the server. The measurement decides that.
- *Records:* no new need; each ending as today, plus whichever detail is ruled.
- *Test coupling:* the eight 60 s hang fakes (§4) become 60 s waits per attempt, unless the fakes change.

**O2 — Close the client on timeout.** Close the connection the abandoned request holds, then continue.
- *Changes:* needs a client per attempt or per call, because `_client` is shared by every thread and `fetch_model_digest` and `server_ps` use it. That moves the 24 alias and 53 patch-string sites, or needs a seam that keeps `_client` as the factory. `analysis/eval/run_qualgap01.py` rebinds `_client`, per the comment at `:68–70`.
- *Cost:* none on a hang, if it works: the retry follows at `L + 30` as now.
- *The measurement decides:* whether closing from another thread unblocks the worker, and whether the server stops generating. If the server keeps generating, the retry still overlaps there.
- *Records:* as O1.

**O3 — Cancel at the server.** This engine has no cancel call. What it has is the restart, and possibly an unload (`keep_alive: 0`), which `12aa_U20P` used on an idle model only.
- *Changes:* depends on what exists. Whether an unload during generation ends the generation is not established; an always-restart makes every timeout a server restart, which the two gates can refuse, and refused means O4's ending.
- *Cost:* 8b: at most about 40 s per timeout on top of L. A restart evicts the model and costs a reload; with a foreign lock it is refused.
- *The measurement decides:* only whether the disconnect is itself the cancel, which would make O3 unnecessary.
- *Records:* a restart per timeout is more of what the row says is unrecorded.

**O4 — Do not retry after a watchdog timeout; record the ending.** The first timeout ends the attempts: go to the restart path or surface.
- *Changes:* the smallest, and the loop's watchdog arm loses its retry. HTTP and other errors keep theirs, where the worker has ended by construction.
- *Cost:* on a hang, less time than today (L, against 3L + 60). It loses recovery from a transient hang: a paper that today succeeds on attempt 2 or 3 becomes a restart or a `model_call_failed`, counted by the consecutive-failure abort (R152). How often that happened is not on disk in a usable form, since `run_calls` records no attempts (row 66); the logs have the "Ollama wall-clock timeout" warnings for runs that have them.
- *Doesn't settle:* a refused restart still leaves one request running at the raise, and the next paper's call starts while it runs. **"No attempt starts" read across calls, not attempts, is not met by O4 alone.** The same is true of O2 if a close doesn't stop the server, and of O1 only up to the read timeout.
- *Records:* the distinction is simplest here, because each ending has one path.

**Across all four:**
- **N23** is met by any option that routes the two arms the same, or by making the limits differ. Neither is forced by the row.
- **N24** is a `finally` on the executor, separate from the choice, at both `:712` and `:855`.
- **F7's re-checks** need `stage` at the post-restart send, and a local import for the environment check, as `run_manifest` imports at call time. Whether a failed re-check closes the run follows the U18–U20 pattern, `MID_RUN_SERVER_REFUSALS`. That is design for the ruling; no option here changes it.
- **Across calls:** the row and the acceptance test speak of attempts. The next paper's first attempt, the next stage's and the snippet retry's are all `ollama_chat` calls that can follow a surfaced timeout (F9).

**Sites classified** (3g): the two `executor` sites and three arms are in scope for every option; `_restart_ollama_and_retry` is in scope for F7 and the endings; `_record` and `:664` for the detail; `run_manifest.record_call` only if a token or an attempt column is ruled; `extractor.restart_ollama` is out of scope; the eleven callers change only under F5's question.

## §7b The B-F14 measurement, designed, not run (2h)

**Proposal only. Nothing below has run. It runs only under a ruling on this read-out (R756(c), R612(n)).**

**The question.** (a) Does closing the client cancel generation on the server? (b) Does a request keep occupying the server after the client's thread is abandoned without closing?

**The instrument.**
- **Model:** `llama3.2:3b` (R741(b)), with `num_ctx` 4096 as the 07:00 health job's check sends, so the load stays small.
- **Lock and scope:** the whole probe inside `with hold_experiment_lock():`, as `12aa_U20P/probe_load.py` took it. Outside any run manifest, writing to no review. Outside 07:00–10:35 UTC.
- **The client:** the installed `ollama` library's `Client` with the engine's timeouts, in the probe script, and not the engine's `ollama_chat`, so that the probe's thread and close are its own. A non-streaming chat, as every engine call is.
- **The request:** one fixed prompt asking for a long counted list, with `num_predict` set so that the baseline runs well past the observation points, and `temperature` 0. Target about 60–120 s of generation. The token count is calibrated by V0: if V0 ends under 40 s or by `done_reason: stop` short of the cap, the probe stops and reports, with no variant sent on a request too short to observe.

**The variants, in order, each from a loaded-and-idle server:**

| Variant | What the client does | What it shows |
|---|---|---|
| V0, baseline | Sends and waits for the response | The full duration D0, the `done_reason`, the journal's line for a completed request |
| V1, client closed | Sends in a worker thread; at about 10 s the main thread closes the httpx client under the library client | Whether the worker unblocks, and when; (a) |
| V2, thread abandoned | Sends in a worker thread; at about 10 s the main thread does nothing to it and stops waiting, as HEAD does | (b) |

After V1 and after V2, at about 12 s, a **follow-up request** is sent on a fresh client: the same model, one token. With `OLLAMA_NUM_PARALLEL=1`, its wall time is the server's answer: about its own short time if the slot is free, about `D0 − 12 s` if the first request still holds it.

**What is read, and when:**
- `/api/ps` before each variant and after the last, for residency and for a foreign model.
- The Ollama journal for the window, after the last variant. Each request's GIN line carries its status and duration, so V1's line says when the server's handler ended and with what status, against V0's.
- The worker's return time and its exception or response, for V1 and V2.
- The follow-up's wall time and its response fields.
- The kernel journal's NVRM lines for the window, and available memory before and after, as readings.

**How it is recorded.** `12ab_U21P/`, in `12aa_U20P/`'s form: `§0 Scope` (purpose, HEAD, timing, what ran, what was not sent), the scripts, raw request and response bodies as sent and received, the event log with timestamps, the journal extract, then one table per question. No design recommendation there.

**Stop conditions, each ending the probe with the lock released and nothing retried:** the lock is held by another process; a foreign model is resident at any `/api/ps`; any non-200 on V0 or a follow-up; V0 too short, as above; a worker still blocked at `D0 + 120 s`; a follow-up with no answer by `D0 + 120 s`; any restart observed (`NRestarts` or service start changed); an unload not confirmed by `/api/ps` within 30 s, reported, with no further action. Nothing restarts the server. A stop leaves its evidence in place.

**End state.** The model unloaded and confirmed; nothing resident; `NRestarts` 0; service start unchanged; fingerprint IDENTICAL.

**What each outcome means for §7:**

| Outcome | Means | Bears on |
|---|---|---|
| V1's handler ends near the close; follow-up fast | A disconnect cancels. The abandoned request's cost is only the open socket | O2 works if closing also unblocks the worker. O1's wait is only the client's |
| V1's handler runs to about D0; follow-up slow | Closing doesn't cancel | O2 and O1 don't stop overlap at the server. O3 or O4 are what remain, and across-calls (F9) stays open |
| V1 closes but the worker stays blocked | Closing from another thread doesn't unblock | O2 needs a different mechanism |
| V2's follow-up fast | The server takes a second request while one runs, or the first ended | `NUM_PARALLEL` isn't the bound assumed; read beside the journal |
| V2's follow-up slow | An abandoned request occupies the slot until done | Confirms the row's premise. HEAD's retry queues behind its own abandoned generation |

Per `12l_P1A.md:158`, "The fix does not depend on the answer; the answer decides only whether an abandoned request still occupies the server." §7 refines that: the answer decides whether O1 and O2 meet the row's words at the server or only at the client.

**Limits of this design.** The small model at a small context stands in for 32b at 131072; a disconnect's effect during prompt evaluation, as opposed to generation, is not sampled, and engine hangs may sit in either. One send per variant: at temperature 0, repeated sends are not draws (R698(e)).

## §8 Findings

**F1.** I2 holds. The entry equals R1, and no ruling closes or re-scopes U21 (§2a). I3 holds; line numbers differ from 12z's as expected ("`ollama_client.py:730–800`" is now `:798–873`).

**F2.** The added fake-client run shows the acceptance test can fail on HEAD: "entries 3 peak concurrent 3 still in flight at the raise 3". Added to the brief's reads; no server, reported in §0.

**F3.** At a limit above the read timeout, the watchdog cannot fire on a silent hang. `r"70b": 1200.0` against `_HTTP_READ_TIMEOUT = 900.0`: every attempt ends in the HTTP arm, and the restart path is never reached. N23 names only equality at 32b. No spec stage uses a 70b model today; only the health job loads it.

**F4.** `except FuturesTimeoutError` at `:722` catches any builtin `TimeoutError` a worker raises, since on this interpreter `concurrent.futures.TimeoutError is TimeoutError` (`.venv/bin/python`: True). So a `TimeoutError` from inside `_client.chat` is logged as a wall-clock timeout and takes the restart path. `httpx.TimeoutException` is not a subclass (MRO read), so the HTTP path isn't affected. Whether anything in that stack raises the builtin was not read.

**F5.** With `max_retries=0`, the first watchdog timeout goes straight to the restart. `ollama_preflight.py:71–72`: "`max_retries=0,`", "`wall_timeout=60.0,`"; `pdf_quality_check.py:107–108`: "`max_retries=0,  # retries handled by outer loop`". So a preflight whose model takes over 60 s to load and answer leads to `sudo systemctl restart ollama`, if the gates allow. The 2026-10-30 health job read `llama3.3:70b` at 102.1 s, not a spec model; the five Ollama models the spec names read 4.3–19.5 s there. `pdf_quality`'s "outer loop" retries would each restart. Not a row today.

**F6.** N24 understates by one site: besides `ollama_chat`'s success path, `_restart_ollama_and_retry` returns at `:867` without shutting its executor down.

**F7.** `docs/architecture/models.md:62` describes the recovery restart as "`sudo systemctl restart ollama` + poll `/api/tags` (60s max)". The code at `:851–852` reads "`Ollama restarted — waiting 10s for stabilization`", "`time.sleep(10)`". The poll belongs to `extractor.restart_ollama`. For HK-ARCH; not edited.

**F8.** The row's "3 requests were still running when `TimeoutError` was raised" holds under a short test limit (FAKE) and at a 60 s limit, not at the stack's own limits. By ARITHMETIC, at the raise the counts are 2 (8b), 1 (27b), and at most the race (32b); the peak is 3 at 8b. The row's premise stands; the number is a test's.

**F9.** The row speaks of attempts, and overlap also crosses calls. After a surfaced timeout with the restart refused, a request is still running (§3's table), and the next `ollama_chat` call, for the next paper, starts while it runs. No option but a performed restart or a verified cancel covers that. Whether the acceptance test should is the ruling's.

**F10.** A restart that recovered is recorded nowhere: `completed`, NULL detail (§5). The four endings don't include it. Row 93's reader says so at `W1-F5.md:90`; the entry's acceptance test doesn't.

**F11.** An error response from the server is retried like a hang: same arm shape, same `retry_delay`. `ollama.ResponseError` reaches `:765` and is retried. It isn't U21's row, but any reshaping of the arms touches it.

**F12.** Interrupts bypass recording: `except Exception` at `:785` doesn't catch `BaseException`, so a `KeyboardInterrupt` or `SystemExit` during `future.result` writes no `run_calls` row and leaves the worker running. A longer wait (O1) makes that likelier. How `run_pipeline` handles an interrupt around it wasn't read here.

**F13.** The census's (iv) count (56 / 26) is broad by construction: its filter is the exception's name. The pins that bind U21 are the ones listed by reading in §4.

## §9 What could not be established read-only

**Q1 — Does closing the client cancel generation on the server?** The row's measurement. §7b, V1. Needs a model call.

**Q2 — Does an abandoned request keep occupying the server?** §7b, V2.

**Q3 — Does closing an httpx client from another thread unblock a read in progress?** §7b, V1. Not read in httpx's or httpcore's source here, and the source wouldn't settle the server side.

**Q4 — How a second request queues at `OLLAMA_NUM_PARALLEL=1`,** and how long it waits. §7b's follow-ups show one case. The server's source wasn't read, and `OLLAMA_MAX_QUEUE` isn't in the pinned environment line.

**Q5 — Whether any response byte reaches the client during a non-streaming generation.** §3's table assumes none, so the read timeout runs from the send. If headers or bytes arrive earlier, the read deadlines move. §7b's journal and worker timings bear on it only indirectly; a direct read would need a capture.

**Q6 — What a restart does to an abandoned thread and to the request it holds.** CODE ORDER gives only that the worker's error lands in an unread future. Needs a restart, which §7b deliberately excludes.

**Q7 — How often a retry has actually recovered.** `run_calls` records no attempts (row 66), and Run 6 predates it. The logs under `data/*/logs/` may hold "Ollama wall-clock timeout" warnings; they weren't read for this, and any count would be of old runs under an older runtime.

**Q8 — An unload during generation:** whether `keep_alive: 0` ends a generation in progress (O3). Not in §7b's variants, which is a decision to keep the probe to the row's question; a ruling can add it.
