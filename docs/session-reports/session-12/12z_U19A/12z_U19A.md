## §3 Mechanism at HEAD (3b)

### §3.1 What the check reads
`_get_ollama_env` runs `systemctl show ollama --property=Environment`. That is the unit's configuration as systemd has it loaded, not the process's environment, though the docstring says "running". It splits the value on whitespace (`raw.split()`), and each `KEY=VAL` token becomes an entry.

On any exception it logs `"Could not read Ollama service environment: %s"` and returns `{}`. It also returns `{}` when the line does not start with `Environment=`. It does not check the return code.

`check_ollama_env` handles drift by tier:
- **Performance tier:** drift is logged only (`"Ollama performance env drift:%s"`).
- **Correctness tier:** drift, or a missing key, raises `RuntimeError("Ollama environment check failed: …")`, which names each key with `expected=` and `actual=`.

An unreadable environment therefore raises naming all three correctness keys as `actual=<not set>`.

### §3.2 When it runs, and what a failure does
`check_ollama_env` has one caller, `require_preflight`, which has five run-path callers (S5–S7).

In `run_pipeline`, `open_run` writes the manifest first (`run_pipeline.py:116`). The extract stage's preflight runs afterwards, inside `_extract_selected` (S5), and the audit stage's inside `_stage_audit` (S6). A preflight `RuntimeError` there leaves through `except Exception` and closes the run `'failed'`, `reason=failure_reason(exc)` ("RuntimeError: Ollama environment check failed: …").

**Row text vs code.** 12l's reading (:550) says the configured environment is checked "only at the start of the extract and audit stages". At HEAD that holds for `run_pipeline`. The FT screener (S7) and the abstract screener also check once, at their own start. Neither restarts proactively, but both can reach S11.

### §3.3 Restarts
**The proactive restart (S8, S9).** After each paper, the loop increments `papers_since_restart`. At `restart_every` (25 by default) it calls `restart_ollama`, which:
- returns `None` after a performed restart once `/api/tags` answers 200;
- also returns `None`, after logging "RESTART SKIPPED", under `EVIDENCE_ENGINE_NO_OLLAMA_RESTART` or a foreign experiment lock;
- raises `RuntimeError` when the restart or the poll fails.

The caller catches `RuntimeError` and continues ("graceful degradation, not crash", `pipeline.md:430`), and resets the counter on any return. Nothing re-reads the environment.

**The recovery restart (S11).** After `1 + max_retries` wall-clock timeouts, `ollama_chat` calls `_restart_ollama_and_retry`. That function restarts, waits 10 s and sends the final attempt through `_client.chat` directly, within the same `ollama_chat` call. A `RuntimeError` from it surfaces as `TimeoutError`, a paper outcome under R532. Nothing re-reads the environment.

So in neither path is anything checked between the restart and the next send, which is the row's clause "nothing re-checks after a restart".

### §3.4 What the running server's environment is, and who can read it (a reading, 2026-10-30)
- `systemctl show ollama -p MainPID` → `2564`, owned by user `ollama`. `/proc/2564/environ` → "Permission denied" for `ankitsarin`. The process's own environment cannot be read without root.
- `systemctl show … -p Environment` → `OLLAMA_KV_CACHE_TYPE=f16 OLLAMA_MAX_LOADED_MODELS=1 OLLAMA_NUM_PARALLEL=1 OLLAMA_FLASH_ATTENTION=true OLLAMA_KEEP_ALIVE=-1` (with `PATH`). `NeedDaemonReload=no`; `ExecMainStartTimestamp=Sat 2026-10-17 23:04:05 UTC`.
- The server writes its own environment to the journal at each start as `msg="server config" env="map[…]"`. 383 such lines are in the journal, and `ankitsarin` can read it through the `adm` group. The line for the current start (2026-10-17T23:04:05Z, `journal_server_config.txt`) carries `OLLAMA_CONTEXT_LENGTH:0 OLLAMA_FLASH_ATTENTION:true OLLAMA_HOST:http://127.0.0.1:11434 OLLAMA_KV_CACHE_TYPE:f16 OLLAMA_MAX_LOADED_MODELS:1 OLLAMA_NUM_PARALLEL:1`. Today the configured and running environments agree.
- An older start in the same journal reads `OLLAMA_CONTEXT_LENGTH:4096 … OLLAMA_FLASH_ATTENTION:false`. This shows the journal line records each start's own values. Its format is Ollama 0.21.0's text, not an interface.

### §3.5 What the manifest records
The manifest body records the following: `libraries` (client library versions), `host` (the machine name), `ollama_host` (U18), `stages` (the stage rows, with digests) and `pins`.
- No key, column or stage row records the server environment or the Ollama server version.
- `grep -n 'OLLAMA_\|Environment\|environ' engine/core/run_manifest.py engine/core/effective_config.py` returns only the `OLLAMA_STAGES` constant and the `ollama_host` reads.

**Constraints on where a reading could go:**
- **At open.** The body is canonical JSON hashed into `manifest_sha256` (S13). A new body key needs no migration, which is the precedent of U18's `ollama_host` ("the ollama_host column owed to 023 (P6)", R728(b)).
- **After open.** The body is written once, before the first call, and never edited: `run_manifests_end_once` permits only the end write. So a reading taken after a restart cannot go into the manifest. Its homes at HEAD are:
  - `run_telemetry` (a JSONL file under the review directory, not the database);
  - the run's `end_reason`, when the reading stops the run;
  - a new table, which would be a migration (023).

### §3.6 OLLAMA_HOST (clause (iii)) after U18
`open_run` refuses a non-loopback host first (`OllamaHostNotLoopback`), so the row's "calls go to another server" is refused for any remote host. A **loopback host on a port other than 11434** passes `open_run` (`is_loopback_host`), and `check_ollama_env` still reads the systemd unit that serves 11434. `server_context_length` guards the same case with `is_local_service_host`; `check_ollama_env` has no such guard. Clause (iii) is therefore partly open (§8 F4).

## §8 Findings

**F1.** INT-j12-17 has no acceptance test in `12f_triage_rows.md` (R514): the row postdates 12f. The only test is the unit entry's `test_the_env_check_runs_again_after_every_restart` (§1.1). (I3: a finding.)

**F2.** At HEAD the environment is first read **after** the manifest is written. `run_pipeline.py:116` opens the run; `extractor.py:1120` and `run_pipeline.py:467` call `require_preflight` later. So "the run manifest stores the environment string read at open" needs a read moved or added before `open_run`. Today there is no read at open to store.

**F3.** A re-check placed inside `restart_ollama` that raised `check_ollama_env`'s `RuntimeError` would be swallowed. S9 reads `except RuntimeError: logger.exception("Proactive Ollama restart failed — continuing without restart. …")`, and that behaviour is pinned by `test_restart_failure_continues_gracefully` and `test_restart_failure_continues_extraction` and documented at `pipeline.md:430`. The same holds for `RunAborted(RuntimeError)`. Only a non-`RuntimeError` class, such as a `RunRefused` subclass, passes it.

**F4.** Clause (iii) is closed by U18 for remote hosts and open for a loopback host on another port. `check_ollama_env` has no `is_local_service_host` guard, while `server_context_length` has `if not is_local_service_host(_client_host()): return None` (§3.6).

**F5.** `restart_ollama` returns `None` both after a performed restart and after a skip. The caller cannot tell the two apart, and T3 pins "a skip resets it as a performed restart does". "A restart is followed by one more environment check" therefore needs a definition of whether a skip counts.

**F6.** The entry's Files list omits `scripts/run_pipeline.py`. That file holds the audit-stage preflight (`:467`), the run open (`:116`) and the close branches (`:199–216`) that an O1 'aborted' clause would join, in R727(b)'s form. It names `engine/migrations/`, which only O6(c) needs.

**F7.** The recovery restart (S11) sends its final attempt within the same `ollama_chat` call, ten seconds after the restart, so a check "before the next paper" cannot cover it (§3.3). The same send is also not preceded by a digest re-read. U18's per-call digest check runs before the attempts loop, not before the post-restart send (`ollama_client.py:730–800`). The model is not re-pulled by a restart, so this is noted, not opened.

**F8.** `journalctl` is not in the test fence's `BLOCKED_COMMANDS` (`tests/conftest.py:64`). An option that reads the journal (O3) would, in any test that reaches it unpatched, read this host's real journal: a world-state fixture defect, not a failure.

**F9.** `docs/architecture/modules.md:381` lists the checked variables as "OLLAMA_FLASH_ATTENTION, OLLAMA_MAX_LOADED_MODELS". The code's `_CORRECTNESS_ENV` also checks `OLLAMA_KV_CACHE_TYPE`, the variable the unit's note names, and warns on `OLLAMA_NUM_PARALLEL`. The doc lags the code.

**F10.** `_get_ollama_env`'s docstring says "running Ollama systemd service" while it reads the loaded unit configuration (`systemctl show`), as L11-C1 found. That is unchanged at HEAD.

**F11.** The FT screener's preflight passes no `spec=` (`ft_screener.py:325`), while the extract and audit callers pass `spec=spec`. This does not bear on the environment check, which takes no spec. Noted from the read, no row.

**F12.** The run's own environment is now observable without root. The server's journal line for the current start (2026-10-17T23:04:05Z) carries the four checked keys at their expected values, and an older start's line carries `OLLAMA_FLASH_ATTENTION:false`, so the line records per-start values (§3.4). That is a reading, not a rule.
