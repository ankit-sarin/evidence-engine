### W1-F2-C2 — `receipts()` converts any `sqlite3.OperationalError` into "no receipts", which `run` reads as a fresh database and `check_drift` reads as no drift
- **File / function:** `engine/migrations/runner.py` :: `receipts`, consumed by `check_drift` and `run`
- **Pattern:** ii
- **Evidence level:** reproduced for `receipts` / `check_drift`; conditional for the consequence inside `run` (condition: an `OperationalError` other than "no such table" at one of `run`'s two receipt reads — e.g. a rollback-journal database whose lock is taken after `ensure_receipts` and held past the 5 s default timeout, or an I/O error on the read)
- **Evidence:**
  - `receipts`: `try: rows = conn.execute("SELECT migration_id, file_sha256, … FROM schema_migrations").fetchall()` / `except sqlite3.OperationalError: return {}` — docstring "`{}` when the store does not exist yet". The handler is not limited to that case; in `run` the store always exists by then (`ensure_receipts(conn)` precedes both reads), so inside `run` the handler can only ever fire for some other fault.
  - `run`: `drifted = check_drift(conn)` … `have = receipts(conn)` / `fresh = (not existed_before) or (not have)` / `if not fresh and not apply_pending:` — with `have == {}` the R222 refusal is skipped and the loop treats every migration as un-applied (`if migration_id in have:` never true), re-executing each and re-writing its receipt through `INSERT OR REPLACE` (original `applied_at` and a `registered_preapplied` mode overwritten by `executed`).
  - Reproducer `W1-F2_2_receipts_swallow.py` (+ `.out`): `unlocked: receipts -> ['002_screening_rename'] | check_drift -> ['002_screening_rename']` · `a plain read under the lock raises: database is locked` · `locked: receipts -> {} | check_drift -> []` · `other-shape receipts table (1 row): receipts -> {}`.
- **What goes wrong:** a transient read fault at that point turns a receipt-bearing, populated database into a "fresh" one: the drift alarm is silenced and every schema migration is run again over live-style data with no `--apply-pending`. This is a second route to B-F02(b)'s end state that does not need the receipts to be absent.
- **Refutation tried:** under WAL (live's mode) a reader is not blocked by a writer, so the lock form needs a rollback-journal database (a restored `.bak` is one — CLAUDE.md: "The copy is switched to a rollback journal") or an I/O fault; a lock held throughout would also fail the first re-executed migration loudly, so damage needs the fault to clear in between. Hence `conditional`. README requires migrations to be idempotent, which bounds the damage if every module honours it (not established — outside the lot; 12f F02 notes 018's unconditional `DROP TABLE IF EXISTS audit_adjudication`).
- **Tests:** none exercises `receipts` under an error; `tests/test_migration_runner.py` covers the absent-table case only (by reading its `runner.run(fresh)` uses, not run).
- **Existing row:** extends B-F02 (b) — same "populated database decided fresh from the receipts table alone", new cause: a swallowed read error rather than absent receipts
- **Proposed class / package:** 1 (latent) / P2 — a swallowed environment fault disables both migration guards at once; fix is one line (catch only the missing-table case).

### W1-F2-C3 — A migration that commits and then loses its receipt is indistinguishable from one never run; "the database then says exactly how far it got" does not hold
- **File / function:** `engine/migrations/runner.py` :: `run`
- **Pattern:** iii
- **Evidence level:** code order
- **Evidence:** `run`: `module.run_migration(str(db_path))` (own connection, own commit) → `conn = sqlite3.connect(str(db_path))` → `conn.execute("PRAGMA foreign_keys = OFF")` → `_write_receipt(conn, migration_id, path, "executed")` → `conn.commit()`. Two transactions on two connections, by design ("One transaction per RECEIPT"). Only the first is inside `try: … except Exception as exc: raise MigrationError(f"{migration_id} failed: …")`; a failure of the reconnect or of the receipt write (a lock, a kill, ENOSPC) leaves the schema migrated, no receipt, and raises a bare `sqlite3` error with no migration id. Stated: `run` docstring "A failure leaves the earlier receipts intact and the failing one absent — the database then says exactly how far it got"; README "so the database says how far it got" and "**Fail-fast**, with the migration id in the message."
  Also in the same lines: `run_migration`'s return value (README: "returns a small summary the log can print") is discarded — not logged by the runner, and the receipt's `note` is always NULL for `executed`, so e.g. what 021's backfill recomputed is recorded nowhere by the runner.
- **What goes wrong:** after such an interruption the database is one migration ahead of its receipts. A receipt-bearing database then refuses every `ReviewDatabase` construction with `PendingMigrations` naming a migration that is already applied, and the documented remedy re-executes it; correctness then rests entirely on that module's idempotence. On a first construction the same window leaves a half-receipted database that is no longer "fresh", so the next open refuses.
- **Refutation tried:** README rule 2 ("It must be **idempotent**") is the intended cover, and the refusal is loud; so no silent corruption was shown — which is why this is class 2, not 1. Not established per module (outside the lot). Grepped the plan for `_write_receipt` / `receipts(conn)`: no row.
- **Tests:** none found for a receipt-write failure (grep of `tests/` for `_write_receipt`: no hit).
- **Existing row:** new (adjacent to class C row C11, which corrected the same docstring's "one transaction per migration" but kept the sentence quoted above)
- **Proposed class / package:** 2 / P6 — loud refusal plus a re-run that depends on per-module idempotence; the sentence is a stated guarantee to correct with it.

- **Refutation tried:** the three explicit `ROLLBACK`s on the `ValueError` paths are correct (a transaction is open there). Checked `in_transaction` semantics: `own_txn` is computed before the `BEGIN`, so it cannot tell "begin failed" from "begun".
