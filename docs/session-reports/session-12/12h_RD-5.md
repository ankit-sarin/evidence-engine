# 12h RD-5 — a manifest that declares stages it does not reach, and the arm pin at a screen-only start (RB-A2, INT-g12-4)

## The question (R563, quoted)

> "No model call, no write, live mode=ro"

> "RD-5 (RB-A2): why a run's manifest declares stages it will not reach, and what pinning the extraction arm at
> a screen-only start does on a real review whose extraction settings later change (refusal path, recovery path,
> which ruling governs arm immutability). Answer: by design and documented, by design but undocumented, or a
> defect, with a proposed class."

> "North star unchanged: these reads inform engine decisions only."

## Answer

**By design but undocumented** — in two parts, which do not stand equally.

1. **Declaring the later stages: by design and documented.** The manifest is written before the first call and
   before any gate is evaluated, and a run may send only what its manifest declared. The run cannot know at open
   whether the adjudication gate will stop it, so it declares every stage from its start stage to the end. This
   is stated in the code and in the plan (R491's note).
2. **Pinning the extraction arm at that open: by design, and its consequence is undocumented.** Pinning at the
   first manifest that names the arm is what R59 rules. What no document states is that the first such manifest
   can be a run that makes no extraction call and writes no claim, and that the pin it leaves is permanent. One
   standing sentence says otherwise: R237's sentence in the project `CLAUDE.md` reads "The first claim-bearing run
   on live pins the arm". In the code the pinning run need not bear a claim.

**Expectation check.** The brief expected "`open_run` declares every stage of the spec regardless of the start
stage, and pins the arm from the spec". The second half held. The first half is located differently and is
narrower: the stage list is built by `scripts/run_pipeline.py`, `_open_run_manifest`, not by `open_run`, and it
is every stage **from the start stage onward**, not every stage of the spec. `open_run` declares exactly what it
is handed. A start at `audit` or `export` names no arm and pins nothing. The answer the brief expected ("by
design but undocumented") is the answer.

`engine/adjudication/workflow.py`, `is_adjudication_complete`, is

Two rules make declaring them necessary rather than tidy: the manifest "is written **before its first model
call**" (`engine/core/run_manifest.py`, module docstring), and under C54 `ollama_chat` refuses a call whose stage
has no `run_stage_configs` row. A manifest that declared only the stages before the gate would have to be a
second manifest after it.

**Documented:** the code comment above; the plan's 12e note, "A screen-only outcome is labelled
`run_kind = 'extraction'`: the manifest declares every stage from the start stage onward (R491; 12e_C55-A)"; and
12g_RB-A's own text for RB-A2, "By design (R73); recorded so the rehearsal's zero-call stages are not read as a
defect".

### Why the arm is pinned at that open

`engine/core/run_manifest.py`, `_stage_arm` and `open_run`:

```python
    if stage in _LOCAL_EXTRACTION_STAGES:
        return spec.extraction_models.arm
```

```python
    stage_list = list(stages) + [f"{CLOUD_STAGE_PREFIX}{a}" for a in cloud_arms]
    arms_by_stage = {s: a for s in stage_list if (a := _stage_arm(spec, s))}
    named_arms = sorted(set(arms_by_stage.values()) | set(arms))
```

Every named arm that is not already pinned is pinned in the manifest's own transaction. The module docstring:

> "An arm that is unregistered, or registered but unpinned, is **pinned at this manifest**: its resolved
> configuration tuple goes into `arms.configuration_json` with `configuration_marker = 'pinned'`,
> `pinned_run_id` and `pinned_sha256`."

So declaring an extraction stage and pinning the extraction arm are one act. The pin covers
(`pin_tuple`): the arm's kind, provider and model; per extraction stage the model, model digest, options hash,
format-schema hash and prompt hash; the codebook's semantic hash; the client library version.

### What a later change of extraction settings does

**Refusal path.** The next run that names the arm resolves it again and compares. `open_run`:

```python
        if name in existing and existing[name][1] == ARM_PINNED:
            if existing[name][2] != sha:
                diff = _diff_keys(json.loads(existing[name][0]), tup)
                raise ArmPinMismatch(
                    f"run refused: arm {name!r} is pinned to a different configuration; "
                    f"this run differs at {diff}. A changed configuration is a new arm "
                    "(R10); declare one in the spec.")
```

It is raised before anything is written, it names the differing keys, and it names its own remedy. Covered by
`tests/test_run_manifest.py` for a changed `options_hash`, `model_digest`, `prompt_hash` and `codebook_hash`.
What moves the pin on a real review between screening and extraction: an edit to the spec's extraction model or
options, or to its `elicitation` flag; an edit to the codebook; a model re-pull that changes a digest; an
`ollama` client upgrade; and an engine change to an extraction prompt. The last is the one an operator does not
make: a review screened on one engine commit and extracted on a later one is refused if any P1 pin-affecting fix
landed between.

**Recovery path.** One only: declare a new arm name in the spec's `arms` block and point
`extraction_models.arm` at it (R10). There is no un-pin. The trigger from migration 020
(`engine/migrations/020_run_manifest.py`, `arms_trigger`) aborts any update of `arm_kind`,
`configuration_json`, `configuration_marker`, `pinned_run_id` or `pinned_sha256` once the arm is pinned:

> "arms: configuration is frozen once the arm holds a claim or is pinned by a manifest, and a pre-manifest arm
> never pins (R21, R59) — a changed configuration is a new arm (R10)"

The superseded arm stays in the registry, pinned, holding no claim. `engine/core/events.py`, `retire_arm`, can
set `retired_at` (the trigger leaves that column free), but it has no caller in `engine/`, `scripts/` or
`analysis/` and no CLI. Until it is retired, `engine/core/effective.py`, `registered_arms`, returns it, and the
default grid (`iter_grid` with `arms=None`), `analysis/paper1/judge_loader.py`, `load_grid`, and
`analysis/paper1/export_disagreement_pairs.py` iterate every registered arm. Not read further: what each of
those renders for an arm with no claims.

**Which ruling governs arm immutability.** Three, in sequence:
- **R10** — "Each arm has a name, a kind (model | human extractor) and one pinned configuration; a changed model,
  prompt, codebook or options is a new arm, never a newer claim in the old one."
- **R21** — "Arms are immutable once they hold a claim: an arm's configuration cannot be re-pinned (a new
  configuration is a new arm, per R10)."
- **R59** — "**Freeze at first manifest, refuse pre-manifest arms.** The R21 freeze widens to "holds a claim OR
  pinned by a manifest"".

R59 is the one that makes a claimless pin permanent. R21 alone would have left a claimless arm re-pinnable.

### The sentence that says otherwise

R237, as transcribed into the project `CLAUDE.md`:

> "No extraction against live before Run 7 on the tagged freshman state. The first claim-bearing run on live pins
> the arm; that run is Run 7."

By the code above, the run that pins the arm is the first run whose manifest declares an extraction stage — any
`run_pipeline` start at `search`, `screen`, `parse` or `extract` — whether or not it reaches extraction or writes
a claim. This is a difference between a ruling's wording and the code's behaviour. It is reported here, not
resolved.

## What this means for the path to Run 7 (CC's reading, from the code; not executed)

The live spec carries `elicitation: false` until the freeze commits the flip. Between now and then, any
`run_pipeline` invocation on live that starts at `search`, `screen`, `parse` or `extract` would, at open and
before any gate, register `local_deepseek_r1_32b` on live and pin it to `defd293b…3e6e`. Run 7, elicited, would
then be refused, and the only way forward would be a new arm name. No such invocation is planned and R237
forbids extraction against live; the point is that the hazard is one step earlier than R237's sentence places
it, and that the step is a start, not a claim.

## Answer in the ruling's categories

**By design but undocumented.**
- The stage declaration is by design and documented.
- The pin at a screen-only start is by design (R59, and the manifest's "before its first call" rule). Its
  consequences — a permanent pin from a run that extracted nothing; the one recovery path; a registered arm left
  with no claims — are written in no operator-facing place, and R237's sentence states the pinning run
  differently.

## PROPOSED class and package

**PROPOSED: Class 2, package P1.** CC proposes; the PI rules.

Class 2 because the failure is a loud refusal that corrupts nothing: the next extraction run stops before any
write and names the remedy. It is not Class 3 because the remedy is not free — a new arm name is a change to the
review's spec and leaves a dead arm in the registry — and because on live the trigger is a single mistaken
command before the freeze. P1 because it is on the Run 7 path.

Options, with their relation to the pin (R539):
- (a) **Wording only.** Correct R237's sentence where it stands in `CLAUDE.md` ("the first run whose manifest
  declares an extraction stage pins the arm, whether or not it extracts"), and state the recovery path beside
  `ArmPinMismatch`. Not pin-affecting. Leaves the behaviour.
- (b) **Pin when extraction starts, not when it is declared.** `open_run` still declares every stage; the arm is
  pinned by the first run that reaches the extract stage (`extraction_digest` already runs there, "before
  anything is selected"). A screen-only run then leaves no pin. Not pin-affecting in R539's sense — the pinned
  value is the same tuple — but it changes when R59's freeze takes hold, so it needs a ruling that amends R59.
- (c) **A refusal on live until the tag.** `run_pipeline` refuses any start at or before `extract` on a review
  whose arm is unpinned unless the tree carries the engine-state tag. Narrow, and it covers only the Run 7
  hazard, not the general one.
- (d) **A supported retire step** for a pinned arm that holds no claim (`retire_arm` exists and has no entry
  point), so the recovery path does not leave a live, empty arm in the grid. Independent of (a)–(c).

CC's PROPOSED choice: **(a) now, in the Class 3 batch's wording pass, and (b) as the fix**, ruled with its R59
amendment. (b) removes the hazard for every review rather than describing it.
