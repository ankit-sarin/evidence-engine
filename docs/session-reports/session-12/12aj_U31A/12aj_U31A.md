## The blocking answer

The row is true at HEAD and wider than it states (FAKE §5, PART 1 and PART 2).

- **A span with no `value` key** is stored as a complete "not reported" claim: value `NR`, snippet empty, one `asserted` event, no
  retry. The snippet the model did send is erased. The acceptance test's first statement is false at HEAD.
- **A list, dict or bool** is stored as Python's `str()` of it: `"['40', '38']"`, `"{'n': 40}"`, `'True'`. With a snippet beside it the
  store accepts each. The second statement is false at HEAD. An int and a float take the same line and are stored as `'40'`, `'40.5'`.
- **An explicit null** yields the canonical sentinel. The third statement is true at HEAD.

Three things the row does not say:

1. **The stored `extracted_data` is not the response as received for these repairs.** The parser patches the span dicts in place, and
   the transport stores that same object. A repaired span reads in `cloud_extractions.extracted_data` as `{"value": "NR",
   "source_snippet": ""}` — the missing key and the model's snippet are gone from the row that is meant to hold the original
   (`engine/cloud/base.py:440–442` says it "stays the response as received"; FAKE shapes 1, 2, 4–9). The response as received survives
   only as `run_calls.response_digest` (a hash) and as `raw_content` in the gitignored telemetry file.
2. **R800(c)'s answer is yes.** A response the transport records as truncated still reaches the parser and the store; a truncated
   response whose text is valid JSON is stored, and one whose cut-off span lacks its `value` is completed with `NR` and stored (FAKE
   T2, T3, T5). §3 Q4.
3. **`scripts/backfill_cloud_spans.py` cannot parse a null at HEAD.** It calls the parser on an instance built by `__new__`, which has
   no `_codebook`; the null branch raises `AttributeError` (FAKE PART 4). `scripts/reparse_cloud_spans.py` builds a real instance and
   would write. §3 Q5.

**If a span were dropped before validation** (CODE ORDER; not built, not driven):

- *Completeness.* `check_completeness` in `extract_with_completeness` (`base.py:551`) finds the field missing. Nothing raises yet:
  the attempt is recorded and the loop re-issues.
- *The re-send.* `extract_with_completeness` (`base.py:548–598`) sends the **identical** request up to `MAX_COMPLETENESS_ATTEMPTS = 3`
  times (`completeness.py:44`). It tells the model nothing about what was wrong: "The request is unchanged between attempts — same
  prompt, same `response_format`, same parameters" (`base.py:536–540`). On the third incomplete attempt it raises
  `IncompleteExtractionError`; each transport's loop catches it, counts the paper failed and does not retry further
  (`openai_extractor.py:182–188`, `anthropic_extractor.py:200–205`).
- *`run_calls` and `extracted_data`.* One `run_calls` row per send, each `completed` (the provider's finish was complete; the row
  records the provider's finish and nothing about content, `base.py:216–223`). Nothing is stored, so there is no `extracted_data`.
  The telemetry file gets one row per attempt with `missing_fields` naming the dropped field (`base.py:554–572`).
- *How the run ends for the paper.* `stats["failed"]` rises by one; the paper has no `cloud_extractions` row and stays pending; the
  run closes `completed` (FAKE T4 shows this path end to end for a field that is absent: three sends, nothing stored, manifest
  `completed`).

There is no partial store on the cloud path: the R140 floor ("the attempt that holds the most fields is stored") is the local event
path's; the cloud loop stores all twenty or nothing.

**If the whole response were refused instead** (the parser returning `[]`, as step 11 does for any validation failure): the same

span is only what the telemetry row says is missing — one field, or twenty.

## §7 Options for the ruling (each with what it records and what it costs; nothing decided here)

**7.1 A span with no `value` key.**
- *(a) Drop the span before validation, so its field reads missing.* Records: a telemetry row naming the field missing; up to three
  identical sends; on exhaustion the paper fails with nothing stored. Costs: up to two more provider calls per affected paper; a
  model that omits the key deterministically fails the paper every time. It is the entry's wording.
- *(b) Refuse the whole response* (return `[]`, as a validation failure does today). Records: the same sends, twenty fields named
  missing. Costs: the same calls; the telemetry no longer says which field was at fault unless the refusal logs it.
- Either way the test `test_null_converted_to_nr` is untouched (it sends an explicit null). Either way step 9's `span.get("value") is
  None` has to become a test on the key (`"value" not in span`), and the snippet erasure for an explicit null stays or goes as a
  separate choice (7.4).

**7.2 A list, dict or bool.**
- *(a) Drop the span* (field missing, re-asked) or *(b) refuse the response* — the same two, the same costs.
- *(c) A list of strings for a field whose text allows several values* is a third case: five fields say "separated by semicolons"
  (Q2). Joining the list with `"; "` would store the codebook's own form, and would invent the separator and the claim that the list
  is the multi-value answer; the codebook declares no multi-value key to decide it by, and the normaliser's hand list names a
  different three. Refusing it re-asks a model that answered in a defensible shape. A list for any other field, a mixed list and a
  dict have no such reading.
- `bool` must be tested before any numeric test (Q2).

**7.3 int and float.**
- *(a) Keep `str()`.* Records nothing new; `'40'` is what a string answer would have been, and `sample_size` is the one numeric
  field (its instruction asks for "a single integer"). Costs: `40.0` is stored as `'40.0'` and the scorer's `parse_number` reads it;
  `NaN` / `Infinity` would store as `'nan'` / `'inf'` unless excluded; a number on a categorical or free-text field is kept too
  unless the rule is narrowed to numeric fields (1 of 20).
- *(b) Refuse as 7.2.* Costs: re-asks for the commonest harmless deviation the original comment names ("Sonnet sometimes returns bare
  numbers for numeric fields like sample_size").
