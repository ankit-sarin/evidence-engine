## §3 Mechanism at HEAD (3b)

1. **Handlers 4 and 5** (CODE ORDER, FAKE).
   - *Route:* `parse_with_vision` calls `ollama_chat` under the `vision_parse` stage. From there `UndeclaredCall` (C54), the `RunRefused` digest/env/context refusals, `CeilingUnavailable`, the recorder's `sqlite3.Error`, and a refused connection (`ConnectionError` / `httpx.Connect*`) can all raise, along with `UndeclaredOverride` from `cfg.with_options` (census #14's list).
   - *Conversion:* each is caught at `:717` / `:806`, recorded as a ledger row (`_record_error`), and wrapped as `ParseFailed(REASON_PARSE_VISION_EXHAUSTED) from exc`. That reaches `parse_all_pdfs:1104`, which writes `parse_failed` / `parse_vision_exhausted` and continues.
   - *The run* is not told; `run_pipeline` closes `completed` if nothing else fails.
   - *FAKE:* all three run-fault members and the KeyError give `paper events: [('parse_failed', 'parse_vision_exhausted')]` and `propagated: no`, with attempt rows 2 (scanned: OCR and vision) or 1 (digital).
2. **Handler 6** (CODE ORDER, FAKE). A gate-failed attempt sends the loop round (`:861–895`). The next tier runs through `_run_parser` (`:899`), whose vision tier is `parse_with_vision`, so the same set as handlers 4–5 when `nxt == "qwen2.5vl"`.
   - `:901–903` records and `break`s, raising nothing.
   - Then `select_attempt` (`:907`, `:411–424`, "First passing attempt, else the least-bad one that actually ran") accepts the earlier gate-failed attempt. `parse_pdf` writes its asset and text and returns.
   - `parse_all_pdfs:1083–1100` then sets `status = 'PDF_EXCLUDED'`, `pdf_exclusion_reason = 'PARSE_QUALITY'` by direct UPDATE.
   - *FAKE:* every case gives `paper events: []`, `asset rows: 1`, `papers.status: ('PDF_EXCLUDED', 'PARSE_QUALITY')`, `stats.failed=0`. A terminal exclusion with no failure event, on an environment fault — "the worst of the set" (triage), confirmed.
3. **Handler 7** (CODE ORDER, FAKE).
   - *Route:* anything raised by `parse_pdf` outside 4–6's wrapping, or after it inside the `try` at `:1077–1103`. That includes the asset transaction's re-raised `sqlite3.Error` (`:978–983`), an `EventRefused` from `record_parsed_text`, a failed `update_status`, and `UnknownStage` from `stage_config("vision_parse", spec)` (`:577`; not a run fault, F2).
   - *Conversion:* `:1120–1128` writes `parse_failed` / `parse_unclassified_error` and continues.
   - *FAKE* (the fault raised from `record_parsed_text`): every case gives `('parse_failed', 'parse_unclassified_error')`, `asset rows: 0` (the transaction rolled back), `parse_attempts rows: 1` (committed by the outer `:997` through `_commit_attempts`).
4. **Handlers 12–13** (CODE ORDER, FAKE). `_commit_attempts` (`:508–526`; docstring "Never raises: a bookkeeping failure must not mask the parse failure the caller is about to report") is called at `:916` (cascade empty) and `:1004` (the outer handler).
   - The only run fault that reaches it in practice is the store's `sqlite3.Error` (census #10: "store `sqlite3` errors on the run's connection only").
   - `:520` logs and rolls back; `:525` swallows a failing rollback.
   - *FAKE* (an INSERT into `parse_attempts` refused): `parse_attempts rows: 0` and the paper still records `parse_failed` / `parse_cascade_empty`. The ledger is lost and the run continues.
   - *Can a run fault there leave a committed parse with no attempt rows?* No, by code order. On the success path the attempt rows are inserted inside the asset transaction (`:972–973`), so a failure there rolls back the asset too (handler `:978`). `_commit_attempts` runs only when no asset was written. The FAKE's other two members at 12–13 are artificial (no model call happens there); they show the catch, not a route.
5. **The run's record.** Every converted case leaves the run open. `run_pipeline` closes `completed` after the PARSE stage unless something else fails (`scripts/run_pipeline.py:197`). Outside a run (`parse_expanded_corpus.py`, `run_id=None`), nothing is written but the log and the stats.
6. **The pins** (CODE ORDER). "Not affecting" holds: the parse stage is not an extraction stage, and neither `vision_parse`'s request nor any pinned tuple is touched by an `except` clause.
